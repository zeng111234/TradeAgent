## Q1. Runtime 怎么设计的

**答案**：

Runtime 是 `backend/app/agent/` 下 12 个模块、约 3700 行，分五层。核心是 `loop.py` 里一个有界 ReAct 循环。

### 一、分层

| 层 | 文件 | 行数 | 职责 |
|---|---|---|---|
| 协议层 | `protocol.py` | 167 | 规范化消息格式 + provider 适配 + 可注入的 `LLMClient` Protocol |
| 工具层 | `tools.py` | 223 | `Tool` / `ToolRegistry` / `@tool` 装饰器 / schema 推导 |
| 循环层 | `loop.py` | 464 | 状态机、预算、轨迹、两条转录不变量 |
| 上下文层 | `context.py` | 272 | token 估算、压缩、溢出可召回 |
| 委派层 | `subagent.py` | 266 | 子 agent、深度约束、只读子注册表 |
| 领域层 | `trade_tools.py` `scan_tools.py` | 745 / 344 | 具体工具（CRM、获客、落盘） |
| 编排层 | `service.py` `scan_runner.py` `repository.py` `render.py` | 177 / 267 / 68 / 689 | 配置→客户端→运行→落库→渲染 |

依赖方向单向：循环层不知道 settings 和数据库，领域层不知道循环。`service.py` 是唯一的接缝。

### 二、协议层：为什么要自己定一套消息格式

`protocol.py` 定义 `Message` / `ToolCall` / `LLMReply` 三个 dataclass，`OpenAICompatibleClient` 负责与 HTTP 格式互转（`:116`）。

**动机是测试**：循环只依赖 `LLMClient` Protocol（`:98`），所以测试里塞一个 `ScriptedLLM` 就能离线、确定性地驱动整个状态机。全部测试不打网络，靠的就是这一层（写这条时是 426 个，现在是 460 个）。

`ToolCall.arguments` 刻意保存**原始字符串**而不是预先解析的 dict，注释写明原因：真实 endpoint 确实会返回非法 JSON，而"从中恢复"是特性不是缺陷。

### 三、循环层：状态机

`AgentLoop.run()`（`loop.py:282`）是 `for round_index in range(1, max_rounds+1)`，每轮：

1. 检查**时间**预算（剩余 ≤ 0 → `truncated / time budget exceeded`）
2. 检查**轮次**预算（在花 model 调用之前）
3. `_ask()` 取模型回复，记 `TraceStep`（thought / tokens）
4. **无工具调用** → 判断是不是有效答案
5. **有工具调用** → 执行，回灌观察结果
6. 检查 **token** 预算

五种终态：`succeeded` / `truncated` / `error` / `stalled` / `running`。

**"有效答案"的判定是这套设计里比较讲究的一处**（`loop.py:314-335`）：

```python
substantive = text and (run.did_investigate or len(text) >= 200)
```

- 已经调用过工具 → 任何文本都算结论
- 没调用过工具 → 除非 ≥200 字，否则不算答案，**回一句"你还没查任何东西，先用工具取证"再给它一轮**
- 连续 3 轮（`max_idle_rounds`）都不动手 → `stalled`

**为什么要这样**：模型可以直接说"最好的客户在德国"而不调任何工具。那不是一个结论，是一个自信措辞的猜测。`did_investigate` 属性（`:236`）把这个区别记录下来了。

### 四、两条转录不变量（这是我觉得最值得看的部分）

**不变量 1：assistant 声明的每个 tool_call 必须恰好收到一个 tool_result，且顺序一致。**

旧代码在预算耗尽时直接 `return`，留下**没有结果的孤儿 tool_call** —— 带孤儿调用的转录在重放时会被 provider 拒绝。现在把批次先切分，再**严格按声明顺序**追加结果。

我修这个问题时**自己又造了一个**：拒绝结果被追加在允许执行的结果之前，结果顺序变成 `[2,3,0,1]`。顺序错乱本身就是隐患 —— 模型重放时会拿错结果对调用。是测试抓到的。

**不变量 2：被 token 上限截断的响应不是有效工具调用。**

`finish_reason` 为 `length` / `max_tokens` 时**整个批次拒绝执行**。理由：被截断的参数**能通过 schema 校验却是残的**（半个 URL、半个正文），执行它就是在损坏状态。拒绝时告诉模型"重新完整地发一次"。

两个不变量都由 `test_agent_loop.py` 的 `_assert_pairing_holds` 覆盖，而且**跑遍所有终止路径**：正常、预算耗尽、批次中途截断、停摆、轮次耗尽。断言的是**序列相等**，不是计数相等。

### 五、预算

`AgentBudget`（`loop.py:98`）有 9 个字段。三套预设实测值：

| | rounds | calls | tokens | seconds | calls/round | ctx budget | keep recent |
|---|---|---|---|---|---|---|---|
| `DEFAULT_BUDGET` | 12 | 25 | 60k | 180 | 5 | 24k | 6 |
| `SCHEDULED_BUDGET` | 10 | 22 | 45k | 300 | 5 | 24k | 6 |
| `CHILD_BUDGET` | 6 | 12 | 30k | 90 | 3 | 12k | 4 |

另有 `max_idle_rounds=3`、`tool_timeout_seconds=60`。

**两个容易忽略的点**：

- `tool_call_count` **只计实际执行的调用**，被拒绝的不计（`:191`）。注释写明：预算表达的是"实际做了多少工作"，而且把拒绝计入会让预算自我否定 —— 一轮拒绝一百次就会把下一轮的预算吃掉。
- `max_tokens` 和 `context_budget_tokens` 是**两件事**：前者是整轮累计上限，后者是**单次请求**上限，超了就触发压缩而不是报错。

### 六、上下文层：压缩 + 可召回

`context.py`。触发条件是 `estimate_tokens(messages) > context_budget_tokens`。

**压缩是确定性的，不是调模型总结**。理由：花一次往返做总结本身可能失败，而一个会幻觉的总结比没有总结更糟。

规则：
- 系统提示 + 最近 `keep_recent_messages` 条**永不裁剪**
- 只有超过 `MIN_TRIMMABLE_CHARS=600` 的旧消息才裁，保留头尾
- 裁掉的部分**写入 spill store**，标记里写文件名，`recall_observation` 工具能读回来
- **`recall_observation` 只在 spill 目录存在时才注册** —— 所以标记里承诺的"可读回"永远是真的，不会是空头支票

**这里我第一次写错了，值得记**：固定 head/tail 每次只释放**固定**数量的 token。每轮新增约 950 而压缩释放约 600，于是请求**无界增长，而每一轮都报告"压缩成功"**。实测：

| | 第 8 轮请求大小（预算 3000） |
|---|---|
| 固定裁剪 | **4696 tokens**，仍在涨 |
| 按缺口缩放 | **2420 tokens**；14 轮峰值 2880 |

压到底还压不下去时，报告 `unreachable: true`，**不假装达成了约束**。

token 估算：散文按 4 字符/token，JSON 这类结构化内容按 3（更密），**刻意低估**是安全方向。

### 七、工具层：schema 从签名推导

`@tool` 装饰器 + `build_params_model()`（`tools.py:217`）从函数签名生成 Pydantic 模型，再 `model_json_schema()` 出 OpenAI 格式。

**实测确认**：Pydantic v2 的 `required` 只列没有默认值的字段，所以可选参数真的是可选的 —— 不需要手写 JSON，也就**不会与实现漂移**。

**失败语义全部是"观察结果"而非异常**（`tools.py:95-132`）：

| 情况 | 行为 |
|---|---|
| 工具抛异常 | 捕获 → `ToolResult.failure("RuntimeError: ...")` |
| 参数非法 JSON | 返回 `not valid JSON` + 收到的原文（截断 200 字） |
| 参数 schema 校验失败 | 返回 `invalid arguments` + `errors()` 详情 |
| 工具名不存在 | 返回 `unknown tool 'x'. Available: ...`，**列出可用工具** |
| 工具超时 | `asyncio.wait_for` → `timed out after 60s`（`loop.py:470`） |
| 返回值不可 JSON 序列化 | `default=str` 兜底 |
| 观察结果 > 4000 字符 | 截断 + 标记总长度 |

`ToolRegistry.call()`（`tools.py:199`）的注释直接写了设计理由：*"未知工具作为失败观察返回而不是抛异常，因为模型能从'这个工具不存在'恢复，而循环不能。"*

### 八、委派层：子 agent

`subagent.py`。`spawn_researcher` 工具给子 agent 独立上下文，只回传结论。

- **深度靠 `ToolRegistry.depth` 强制**，默认 `max_depth=1`。到顶时**工具仍然可见，是调用被拒绝并说明原因** —— 藏起来会让模型无法知道"委派存在但已耗尽"，它就永远不会尝试也永远不会解释。
- **子注册表是新建的**，从父表减去委派工具、减去带 `write` 标签的。理由：子 agent 如果能拿到扫描的 `save_prospects`，就是在从父 agent 看不见的上下文里写父 agent 的输出。
- 子 agent 失败**不会中断父 run**。
- 实测子注册表：`['classify_prospect','get_communication_history','get_customer','get_customer_signals','inspect_website','list_customers','search_prospects']` —— 无委派、无写工具、depth=1。

### 九、权限：靠工具不存在

注册表里**没有** `send_*` / `delete_*` / 修改已有客户或邮件记录的工具。基础注册表实测 10 个工具，其中只有两个能写（`create_email_draft` 只存 `pending` 草稿，`upsert_customer` 遇到已存在直接 `skipped`）。

有测试扫整个 agent 包，确认**没有任何 SMTP 引用**。

**边界不靠提示词，靠能力缺失** —— 一条提示词可以被绕过，一个不存在的工具不行。

### 十、和 pi / DSH 的关系

我对照了两个生产级 harness（pi 的 `agent-loop.ts` 源码 + DSH 公开文档），结论有两点：

1. **"有界循环"是我加的，不是抄的。** Pi 的 `runLoop` **没有任何**步数/轮次/token/墙钟上限（源码 grep 零命中）；DSH **明确把"没有轮次预算"写成设计取舍**，留了 `agent/turn-stopping` 钩子给使用者。DSH 自己的 field report 记录了一次 **72 步的单轮**。所以 `AgentBudget` 是两家都留给实现者的那一块。

2. **不变量 1、2 是从它们那儿补上的。** DSH 用 `TOOL_OUTCOME_UNKNOWN` / `TOOL_NOT_STARTED` 保转录配对；Pi 拒绝执行 `stopReason: "length"` 的整批调用。我原本两条都缺。

**刻意没采纳的**：DSH 的四层权限栈（closed approval vocabulary / session `ask`|`never` / per-call sandbox mode / 审计事件不入模型上下文）。它要中介任意文件系统与进程访问；我只需要"不发邮件"，靠注册表里没有这个工具就够了，不需要一个可能出错的策略引擎。

**依据**：`backend/app/agent/` 全部 12 个模块；`AgentBudget` 与三套预设由 REPL 实测打印；子注册表内容实测；对照结论来自 pi 源码（`badlogic/pi-mono` → `packages/agent/src/agent-loop.ts`）与 DSH 公开文档。

**置信度**：
- 分层、状态机、两条不变量、预算数值、压缩算法、工具失败语义、委派深度 —— **从代码读出 + 常量实测打印**
- 压缩缩放前后的 4696 → 2420 对比 —— **实测**（`_probe2.py`，跑完已删）
- pi/DSH 对照 —— **来自子 agent 的调研报告**，它声称读了 `agent-loop.ts` 源码；我**没有亲自复核**那两个仓库
- 真实模型下能跑通（4 轮 / 10 次调用 / 1 次被拒 / 10 秒）—— **实测**（DeepSeek，两次）

**未验证部分**：
- **我没测量过 24k 的 `context_budget_tokens` 和 60k 的 `max_tokens` 是否合理。** DeepSeek 的实际上下文窗口我没查，这两个数是按"够用且不失控"定的，不是按模型能力算的。长时间多轮的真实分布我没有数据。
- **真并发下的行为我不知道。** 单进程跑过，没试过两个 run *同时* 跑。（原本还有一条更严重的：两个 run 先后跑会互相污染委派状态 —— `ToolRegistry` 被就地改写、`spawn_researcher` 闭包绑着上一次运行的记录。这条已修，见 Q2 与提交 `b67024a`，有复现脚本和回归测试。）
- **`max_seconds=300` 的定时任务（`SCHEDULED_BUDGET`）我从来没在 CI 里真跑过。** 我只在本地跑过 180 秒的默认预算。

## Q2. 架构怎么设计的

**答案**：

一句话：**一条 FastAPI 主干，三个入口共用一套有界 agent runtime；AI 调用原本有两套栈，我这次把第二套接到同一个 provider 接缝上。**

### 一、主干

`main.py` 起 FastAPI，lifespan 里做三件事：建表 → 插演示数据 → 起 APScheduler。六个 router 全挂在 `/api/v1` 下。

| 层 | 位置 | 说明 |
|---|---|---|
| 入口层 | `main.py` + `routers/`（6 个） | HTTP；`/scheduler/*` 两个路由直接写在 `main.py` 里 |
| agent runtime | `app/agent/`（12 模块 3757 行） | 见 Q1 |
| legacy AI | `services/agent_service.py`(1093) `services/ai_service.py` `workflows.py`(465) | 关键词分类器 + 直连模型 |
| 共享策略 | `services/follow_up_policy.py`(257) | 阈值唯一来源，两端都用它 |
| 数据层 | `models/` `schemas/` `database.py` | SQLAlchemy async + SQLite |
| 前端 | Vue3 + Vite，dev 代理 `/api` → :8000 | 8 个 view，轨迹用 Mermaid 自渲染 |

依赖方向单向：`routers → services → models`。**唯一一处反向**是 `agent/trade_tools.py:98` 导入 `services/follow_up_policy.py` —— 那是个纯函数模块（没有数据库、没有 IO），放 `services/` 下只是历史位置，它是共享内核而不是上层。

### 二、三个入口，一个 runtime

| 入口 | 路径 | 特点 |
|---|---|---|
| HTTP | `POST /api/v1/agent/run` | **同步**，把整条轨迹一起返回 |
| CLI | `app/cli.py` → `run` / `tools` / `runs` / `show` | 无前端也能跑 |
| 定时 | APScheduler → `workflows.daily_morning_routine` → `find_leads_agentic` | 走 `SCHEDULED_BUDGET` |

三者最后都进 `agent/service.execute()`，落库到 `agent_runs` 表，被 `/agent/runs/{id}/trace.html` 渲染成一张能单独保存的 HTML 页面。

### 三、两套 AI 栈 —— 这是原架构里最大的问题

runtime 那一套是干净的：`agent/protocol.py` 定义规范化消息、工具 schema、`finish_reason` 处理，client 可注入（所以能离线测）。

**但库里另外还有 10 处自己 `AsyncOpenAI(...)`**（`agent_service.py` 8 处、`ai_service.py` 1 处、`workflows.py` 1 处）。实测这 10 处：

- **没有一处传 timeout** → 用的是 openai SDK 默认 **600 秒**
- **没有一处看 `finish_reason`** → 被 `max_tokens` 截断的回答会被当成完整回答
- **有 7 份复制粘贴的 ` ``` ` 剥离**，每份都写 `content.split("```")[1]`，闭括号之后的内容全留着

不是洁癖问题。`max_tokens=300` 用来写一封邮件，截断是常态；截断后的半封邮件会被 `.strip()` 存成 `draft_email` / `rescue_email` 交给用户点发送。

### 四、这次改了什么

1. **`app/llm.py`**：唯一接缝。缓存 client、显式 120s 超时（`OPENAI_TIMEOUT_SECONDS`）、`finish_reason` 命中 token 上限就抛 `LLMTruncated`（**不当成部分文本返回**）、fence 剥离与 JSON 解析各一份。
2. **10 处裸调用 → 0 处**。AST 守卫测试：全库只有 `app/llm.py` 和 `agent/protocol.py` 能构造 provider client、能调 `chat.completions.create`。
3. **如实标注**：`ai_powered` / `fallback_reason`。这两个字段本来就有 —— `analyze_email_reply`、`analyze_inquiry`、`negotiation`、`website`、`churn` 五个函数都带 —— **唯独两个真正写邮件的不带**，其中 `generate_cold_email` 在 key 错、超时、限流时都会静默返回一份硬编码模板。现在三条路径分别报 `no_api_key` / 截断 / 调用失败，前端出徽标。
4. **`scan_leads_draft_workflow` 读的是 `lead["draft_email"]`，而扫描器从来不设这个键** → 那个"AI 生成的草稿"列表里，每一封正文都是内联的一行模板、每一封标题都是同一句 `Partnership Inquiry - X from China`，而 UI 让用户批准并发送。现在真的调 `_generate_lead_draft_email()`。
5. **删掉 `ai_service.analyze_customer_match`** —— 死代码（除测试无人调用），用关键词重叠造一个 0–100 的"匹配分"。项目自己有一条"排序必须是模型判断"的守卫测试，这个函数正好从它的缝里漏过去。

**实测**：真模型（DeepSeek `deepseek-chat`）两条邮件路径都 `ai_powered=True`、无 fallback，5.5 秒；**460 个测试通过，8.4 秒**；前端 `npm run build` 通过。

### 五、还是没做的

- **两套栈仍然并存。** legacy 那 8 个函数还有自己的 prompt 和关键词分类器，没改成工具调用 —— `agent_service.py` 里 `_basic_reply_analysis` / `_basic_inquiry_analysis` / `_basic_analyze_website` 都还在，`test_characterize_classifiers.py` 正钉着它们的现状（包括"no rush 被判 high"那个已知 bug）。
- **`POST /agent/run` 是同步的**，一个 run 最长占住连接 180 秒。
- **真并发没测过**（先后跑会互相污染的问题已修）。

**依据**：`backend/app/` 全树；10 处裸调用与 7 份 fence 剥离由 `Select-String` 计数；`ai_powered` 的分布由 `Select-String` 计数；真模型结果来自 `scripts/smoke_legacy_llm.py` 输出；测试数与耗时来自 `pytest` 末行。

**置信度**：
- 主干分层、依赖方向、三个入口、两套栈、10 处调用、7 份剥离 —— **从代码读出 + 命令计数**
- 「截断的半封邮件会被存成草稿」—— **从代码读出**（`.strip()` 直接赋给 `draft_email`，且没有 `finish_reason` 判断）；**我没有真的造出一次截断来复现**，但 `max_tokens=300` 写一封 100 词英文邮件是紧的
- 「那个草稿列表全是模板」—— **实测**：`scan_runner.py` 构造 lead 时只设 13 个键，不含 `draft_email`，所以 `lead.get("draft_email","")` 恒为空
- 真模型跑通 —— **实测**（DeepSeek，一次）

**未验证部分**：
- 换成 MiMo / OpenAI 官方 endpoint 没验过，只验了 DeepSeek。
- legacy 那 8 个函数在**真实模型下**的截断率我没有数据；我只证明了截断会被正确处理，没证明它多常发生。

## Q3. 这个 agent 的"一次任务"是什么？边界在哪？

**答案**：

一句话：**一次任务 = 一个 goal + 一个 run id + 一个 deadline 的整棵运行树**（父 run 加它派生的所有子 run）。**不是一个 loop** —— 这个区别原来没有落实，下面第三节是我实测出来的漏口。

### 一、任务的起止

- **开始**：有人给出 goal。三个入口（HTTP `POST /agent/run`、CLI、APScheduler 定时扫描）最后都进 `agent/service.execute()`。
- **结束**：五种终态 `succeeded` / `truncated` / `error` / `stalled`（还有运行中的 `running`）。`truncated` 会说明是哪一条预算用尽了。
- **落库**：`agent_runs` 表一行一条，`run_id` 是 uuid4。
- **没有的东西**：没有队列、没有重试、没有跨任务的会话记忆。第二次跑就是第二个任务，除了数据库状态和本次的 spill 目录，什么都不共享。

### 二、七道边界

| 边界 | 值 | 靠什么强制 |
|---|---|---|
| 轮次 | `max_rounds=12` | 在花掉 model 调用**之前**检查 |
| 工具调用 | `max_tool_calls=25` | 超出的**先切分再按声明顺序拒绝**，理由回灌给模型 |
| token | `max_tokens=60k` | 累计，超了 `truncated` |
| 墙钟 | `max_seconds=180` | **整棵树的 deadline**（见第三节） |
| 单轮调用数 | `max_calls_per_round=5` | 超出部分拒绝 |
| 委派深度 | `max_depth=1` | 子注册表构造时就去掉委派工具；到顶时工具仍可见、调用被拒并说明原因 |
| 写权限 | 注册表里**没有** `send_*` / `delete_*` | 只有 2 个写工具，草稿只写 `pending` |

知识边界也在这里：它只知道工具返回过的东西，加上 spill store 里能按名字召回的被裁剪观察结果。

### 三、实测出来的问题：边界原来只画在单个 loop 上

每个 loop 有自己的天花板，而委派会开出新的 loop。父 run 把一轮的开销只在**轮次开始时**记一次账，所以那一轮里派生出去的工作全是免费的。

复现（父预算 1 秒，一轮里两次委派，子预算 10 秒）：

| | 值 |
|---|---|
| 父 `max_seconds` | 1.0 |
| 父 `run.elapsed` | **2.42s**（超 1.42s） |
| 父上报 | 1 次工具调用 / 230 tokens |
| 任务实际 | **3 次工具调用 / 1150 tokens** |

按生产预设放大：`180 + 5 × 90 = 630` 秒，而 `agent_runs.py` 的注释承诺"一个 run 最多占住连接 `max_seconds`"。**注释是假的。**

**修法**：deadline 继承，而不是各自重新计时。

1. loop 算出**一个绝对 deadline**（`start + max_seconds`），已有 deadline 的取更早的那个。
2. 父把 deadline 作为**宿主参数** `_deadline` 传给工具 —— 以下划线开头的参数不进 schema，模型看不见也伪造不了（有测试：模型传 `_deadline=999` 会被忽略，宿主传 `123` 才生效）。**模型能写的 deadline 不是 deadline。**
3. 子 agent 的额度取三者最小：自己 90s、父还剩多少、**父的每次调用上限**。
4. 工具自己的 timeout 按"还剩多少"夹紧，超时消息也改成"运行时间预算用完了"而不是谎报"timed out after 60s"。
5. 一轮里 deadline 过后剩下的调用记为 `run_deadline_reached`，不再执行。
6. 真的被取消时，记录**取消**——原来一个被取消的子 agent 留下的是 `ok=False` + `error=''` + 没有 run，`spawned: 1` 却没有任何解释。

顺带查出的第二个问题：**子 agent 的 90 秒额度落在父的 60 秒每次调用上限后面**，所以它永远在 60 秒被取消，什么都带不回来。现在它拿到较小的那个数，自己停下来并把已经查到的结果交回（留 0.25s 收尾余量，常量 `DEFAULT_UNWIND_SECONDS`）。

### 四、账目：父的计数看不见子 agent 的工作

这是"边界在哪"的另一半。同一个任务，父的计数器只报自己的。现在：

- `service.summarise()` 同时给 `tool_calls`（父）和 `tool_calls_total` / `tokens_total` / `delegations`（任务）
- `GET/POST /agent/run` 的响应模型加上这几个字段（不加的话 FastAPI 会直接丢掉）
- trace 页表头在发生委派时多一行："sub-agents：N（不计入以上数字）"

真模型实测（`scripts/smoke_delegation.py`，DeepSeek）：一个子 agent 跑了 **5 次工具调用 / 7730 tokens / 21.3s**，返回了带证据的答案，而父自身的计数是 0 —— 正是这些数字原来会消失的地方。

### 五、刻意不做的边界

- **`POST /agent/run` 仍然是同步的**，一个任务会占住连接直到 deadline。
- **`agent_runs` 表没有委派相关列**，所以列表页的数字仍然是父 loop 的。加列需要迁移，而本项目只有 `create_all()`（它不会 `ALTER TABLE`），给现有库加列会让运行中的实例炸掉 —— 这是明确的取舍，不是漏掉。
- 没有并发上限。子 agent 是串行的（一次一个），但两个 `POST /agent/run` 会各自跑。

**依据**：`backend/app/agent/loop.py`、`subagent.py`、`tools.py`、`service.py`、`render.py`；超时数值来自 `_probe_boundary.py` 的输出（临时探针，跑完已删，同样的场景现在由 `tests/test_agent_task_boundary.py` 12 个测试覆盖）；真模型数字来自 `scripts/smoke_delegation.py`；测试 472 个通过（9.8 秒）。

**置信度**：
- 起止、七道边界、五种终态、没有队列/重试/记忆 —— **从代码读出**
- 2.42s 超时、1 vs 3 次调用、230 vs 1150 tokens —— **实测**（探针）
- 630 秒最坏值 —— **算术**：同一个组合规则套生产预设，我没有按 630 秒真跑过
- 91 行那个"子 agent 被父的调用上限取消" —— **实测**（探针日志里 `delegation.error=''`、`run=None`）
- 真模型委派跑通 —— **实测**（DeepSeek，一次）

**未验证部分**：
- **真并发没测过。** 两个 `POST /agent/run` 同时打进来会怎样，我没有数据。先后跑会互相污染的问题已经在 `b67024a` 修掉。
- **`DEFAULT_UNWIND_SECONDS = 0.25` 是我定的，不是量出来的。** 它只需要大于"子 agent 从时间检查到返回"的开销，我没有测过那个开销的真实分布。
- **630 秒那一档没有跑过**，只跑了 1 秒和 0.3 秒量级的探针。

## Q4. 客户先回了你第 3 封邮件，前两封还没回 —— 状态机怎么表达？

**答案**：

**原来表达不了，而且它说的是反话。** 现在能表达了，表达方式是：**一个会话（thread），不是三个消息。**

### 一、原来的状态机长什么样

- `EmailLog.status`：`pending → sent → delivered → opened → replied`，还有 `bounced` / `failed`。**一条出站记录一个状态。**
- `EmailLog.replied_at`：这一封的回复时间。
- `Customer.stage`：`new / contacted / interested / quoting / completed / lost`。
- 没有的东西：**没有方向**（`email_logs` 只存我们自己发出去的，没有任何地方能存一封收进来的信）、**没有 thread id**、**没有 `in_reply_to`**、**没有序号**。

### 二、两个实测出来的硬伤

**硬伤 1：`REPLIED` 这个状态进不去。** 全库只有三条状态转换被实现：`PENDING → SENT|FAILED`（发送）、`SENT → OPENED`（追踪像素）。`PUT /emails/logs/{id}` 只能改 subject/body/to_email。**没有任何 endpoint、workflow 或 agent 工具写过 `replied_at` 或 `status=replied`。**

后果不是"少个功能"，是**好几个数字在撒谎**：

- `/emails/stats` 的 `reply_rate = total_replied / total_sent` —— 分子恒为 0，所以**这个比率按构造永远是 0.0%**。
- `ChurnPolicy.no_reply_critical_emails = 3`：**凡是发过 3 封的客户一律 critical**，理由"Sent 3 emails, received 0 replies"，因为回复记不下来。
- agent 的 `get_customer_signals` 对每个客户都报 `has_any_reply: false`，永远。

**硬伤 2：账算在了消息上，而不是会话上。** 就算回复记下来了，`assess_churn` 数的是"发过几封、几封被回复"，`assess_follow_up` 则**完全不看回复**，只看"距上一封多久"。实测：

| 读法 | 结果 |
|---|---|
| 今天（回复记不下来） | `critical`：**"Sent 3 emails, received 0 replies"** → 建议"换个渠道试试（WhatsApp/电话）" |
| 假如回复记下来了 | `None`：**毫无风险** |

两个答案都是错的。而 follow-up 列表对同一个客户给的是：

```
('high', 'No reply in 8 days', 'Send a follow-up email with different angle')
```

—— 对一个两天前刚回信的客户说"8 天没回复，换个角度再追一封"。

### 三、正确的模型：会话，不是消息

一次回复是**会话上的事件**，不是某一条消息的属性。该问的从来不是"第 2 封被回复了吗"，而是**"谁最后说话，谁欠谁一个回复"**。三件事随之改变：

1. **在第一次回复之前发出去的信是"被越过（superseded）"，不是"被无视"。** 客户回了第 3 封，不等于他无视了前两封 —— 会话往前走了。追着问第 1 封是噪音。
2. **最后一次回复之后发出去的信才是"在等回复（awaiting_reply）"。** 这才是 "no reply" 规则该数的东西。
3. **如果会话里最新的是"他们"的信，那沉默的是我们。** 这一条原来的规则**完全看不见**：它数出站行、看出站时间戳，所以昨天刚回信的客户读起来是"发了 3 封，0 回复"。

### 四、改了什么

1. **`derive_thread_state(emails, now)`**（`follow_up_policy.py`，纯函数）：从出站行里推出 `outbound / superseded / awaiting_reply / answered / they_wrote_last / reply_owed_days`，以及两个时间戳。这是整个答案的核心。
   - 判定"被回复"看 `replied_at`，**不看 status** —— 时间戳是事实，枚举是记账，现实里两者会不一致（有测试）。
   - `bounced` / `failed` 不算 outbound：没送达的信不在等回复。

2. **补上唯一缺失的写路径**：`POST /api/v1/emails/logs/{email_id}/reply`。
   - **幂等**：同一条再记一次不会移动时间戳（"回复发生过一次"）。
   - **不改 stage**：回复是接触，不是阶段跃迁；系统自作主张把 `contacted` 改成 `interested` 是另一个猜测装成事实。
   - 拒绝：未送达的信（409，"一封没发出去的信不可能被回复"）、未来时间（422）、**早于发信时间的回复（422）** —— 后者会让整个推导变成胡话（所有信都显得在回复之后发出，于是没有一封在等回复，会话读起来像已结案）。
   - 记完返回推导出来的会话状态，调用方立刻能看到效果。

3. **规则改成读会话**：
   - `assess_churn` 新增规则 0：`they_wrote_last` → 按 `reply_owed_critical_after_days=2` 升级为 critical，理由"Customer replied 2 day(s) ago and has not heard back"，动作"Answer their message. They wrote last, so the delay is ours."；"no reply" 规则改数 `awaiting_reply`。
   - `assess_follow_up`：`they_wrote_last` **排在 quoting/interested 之前**（这不是程度问题，是唯一一个下一步动作没有歧义的）；已回复且不欠回复 → "Conversation answered N day(s) ago; waiting on them"，**不再出现 "No reply in N days"**。
   - 两个函数都保留 `thread=None` 的旧行为，好让边界测试一次只验一条规则；**但生产里没有任何调用点可以不传** —— 有 AST 守卫测试盯这一点（我临时删掉一处 `thread=thread` 验证过它真会红）。

4. **agent 侧** `get_customer_assessment` 多返回 `conversation` 块和 `emails_awaiting_reply` / `emails_superseded_by_a_reply` / `they_wrote_last`，`note` 里明说"读数字之前先读 conversation"。churn / follow-up 两个接口的返回里也带上 `conversation`。

5. **前端** `/emails` 的日志表加了一列"Mark replied"（只有 sent/opened/delivered 才出现），点了会告诉你"你欠他们一个回复"。没有这个按钮，新状态在界面上仍然进不去。

**实测**（HTTP 全链路，`tests/test_reply_endpoint.py`）：给同一客户发 3 封 → 第 3 封记回复 →
`outbound=3, superseded=2, awaiting_reply=0, they_wrote_last=True`；前两封仍然是 `sent`（没有被抹掉）；follow-up 那条从"Recently contacted, wait for reply"变成 **"They replied 0 day(s) ago and have not heard back" + "Answer their message"**；再点一次不移动时间戳；`total_replied` 不再是 0。

**498 个测试通过**（原 472），10.3 秒；前端 build 通过。

### 五、还没做的部分

- **没有入站消息表。** 回复仍只是出站行上的一个时间戳：存不下"他们说了什么"，也存不下"这封回的是哪一封"（`in_reply_to`）。要真正做对话，需要一张 `email_messages` 表（方向 + message_id + 线程），而**加列是不可能的**：`init_db()` 只 `create_all()`，不会 `ALTER TABLE`，给运行中的库加列会炸。**加表是安全的**（`create_all` 会建缺失的表），所以这是下一步该走的路，不是可以顺手改的。
- **回复内容不进 agent 的上下文。** agent 能看到"他们回了"，看不到回了什么。`analyze_email_reply` 是独立的接口，要人把邮件正文粘进去。

**依据**：`app/models/email_log.py`、`app/routers/emails.py`、`app/services/follow_up_policy.py`、`app/services/agent_service.py`、`app/agent/trade_tools.py`；"没有任何写路径"由 `Select-String` 全库扫描确认（`replied_at =` 与 `status = EmailStatus.REPLIED` 在改动前 0 命中）；两种错误读法由命令行实测打印；HTTP 全链路结果来自 `tests/test_reply_endpoint.py`。

**置信度**：
- 三条状态转换、没有方向/线程/序号、`reply_rate` 恒为 0 —— **从代码读出 + 全库扫描**
- 表格里那两种错误读法、以及 "No reply in 8 days" —— **实测**
- 新模型对场景的读数 —— **实测**（纯函数 + HTTP 两层）
- "加列会炸" —— **从代码读出**（`init_db()` 只有 `create_all()`）；我没有拿一个旧库真的试过

**未验证部分**：
- **真实的 SMTP 往返没测过。** 测试里发送是模拟的（没有 SMTP 凭据），所以"发送成功后状态是 sent"是模拟路径。真发信走的是另一支。
- **没有真实客户数据。** 演示库里所有客户的 `email_logs` 都是空的（这也是之前那次真模型运行发现"notes 说联系过、日志说没联系过"的原因）。所以"superseded 会有几个"只有构造的数据。
- **`reply_owed_critical_after_days = 2` 是我定的**，不是从数据里量出来的。它是一个观点，现在至少是一个**有名字、能改、有边界测试**的观点。
