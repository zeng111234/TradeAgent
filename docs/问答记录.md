## Q1. Runtime 怎么设计的

**答案**：

Runtime 是 `backend/app/agent/` 下 12 个模块、约 3700 行，分五层。核心是 `loop.py` 里一个有界 ReAct 循环。

### 一、分层

| 层 | 文件 | 行数 | 职责 |
|---|---|---|---|
| 协议层 | `protocol.py` | 167 | 规范化消息格式 + provider 适配 + 可注入的 `LLMClient` Protocol |
| 工具层 | `tools.py` | 223 | `Tool` / `ToolRegistry` / `@tool` 装饰器 / schema 推导 |
| 循环层 | `loop.py` | 464 | 状态机、预算、轨迹、两条转录不变量 |
| 上下文层 | `context.py` | 272 | token 估算、压缩、溢出可召回 |
| 委派层 | `subagent.py` | 266 | 子 agent、深度约束、只读子注册表 |
| 领域层 | `trade_tools.py` `scan_tools.py` | 745 / 344 | 具体工具（CRM、获客、落盘） |
| 编排层 | `service.py` `scan_runner.py` `repository.py` `render.py` | 177 / 267 / 68 / 689 | 配置→客户端→运行→落库→渲染 |

依赖方向单向：循环层不知道 settings 和数据库，领域层不知道循环。`service.py` 是唯一的接缝。

### 二、协议层：为什么要自己定一套消息格式

`protocol.py` 定义 `Message` / `ToolCall` / `LLMReply` 三个 dataclass，`OpenAICompatibleClient` 负责与 HTTP 格式互转（`:116`）。

**动机是测试**：循环只依赖 `LLMClient` Protocol（`:98`），所以测试里塞一个 `ScriptedLLM` 就能离线、确定性地驱动整个状态机。全部测试不打网络，靠的就是这一层（写这条时是 426 个，现在是 460 个）。

`ToolCall.arguments` 刻意保存**原始字符串**而不是预先解析的 dict，注释写明原因：真实 endpoint 确实会返回非法 JSON，而"从中恢复"是特性不是缺陷。

### 三、循环层：状态机

`AgentLoop.run()`（`loop.py:282`）是 `for round_index in range(1, max_rounds+1)`，每轮：

1. 检查**时间**预算（剩余 ≤ 0 → `truncated / time budget exceeded`）
2. 检查**轮次**预算（在花 model 调用之前）
3. `_ask()` 取模型回复，记 `TraceStep`（thought / tokens）
4. **无工具调用** → 判断是不是有效答案
5. **有工具调用** → 执行，回灌观察结果
6. 检查 **token** 预算

五种终态：`succeeded` / `truncated` / `error` / `stalled` / `running`。

**"有效答案"的判定是这套设计里比较讲究的一处**（`loop.py:314-335`）：

```python
substantive = text and (run.did_investigate or len(text) >= 200)
```

- 已经调用过工具 → 任何文本都算结论
- 没调用过工具 → 除非 ≥200 字，否则不算答案，**回一句"你还没查任何东西，先用工具取证"再给它一轮**
- 连续 3 轮（`max_idle_rounds`）都不动手 → `stalled`

**为什么要这样**：模型可以直接说"最好的客户在德国"而不调任何工具。那不是一个结论，是一个自信措辞的猜测。`did_investigate` 属性（`:236`）把这个区别记录下来了。

### 四、两条转录不变量（这是我觉得最值得看的部分）

**不变量 1：assistant 声明的每个 tool_call 必须恰好收到一个 tool_result，且顺序一致。**

旧代码在预算耗尽时直接 `return`，留下**没有结果的孤儿 tool_call** —— 带孤儿调用的转录在重放时会被 provider 拒绝。现在把批次先切分，再**严格按声明顺序**追加结果。

我修这个问题时**自己又造了一个**：拒绝结果被追加在允许执行的结果之前，结果顺序变成 `[2,3,0,1]`。顺序错乱本身就是隐患 —— 模型重放时会拿错结果对调用。是测试抓到的。

**不变量 2：被 token 上限截断的响应不是有效工具调用。**

`finish_reason` 为 `length` / `max_tokens` 时**整个批次拒绝执行**。理由：被截断的参数**能通过 schema 校验却是残的**（半个 URL、半个正文），执行它就是在损坏状态。拒绝时告诉模型"重新完整地发一次"。

两个不变量都由 `test_agent_loop.py` 的 `_assert_pairing_holds` 覆盖，而且**跑遍所有终止路径**：正常、预算耗尽、批次中途截断、停摆、轮次耗尽。断言的是**序列相等**，不是计数相等。

### 五、预算

`AgentBudget`（`loop.py:98`）有 9 个字段。三套预设实测值：

| | rounds | calls | tokens | seconds | calls/round | ctx budget | keep recent |
|---|---|---|---|---|---|---|---|
| `DEFAULT_BUDGET` | 12 | 25 | 60k | 180 | 5 | 24k | 6 |
| `SCHEDULED_BUDGET` | 10 | 22 | 45k | 300 | 5 | 24k | 6 |
| `CHILD_BUDGET` | 6 | 12 | 30k | 90 | 3 | 12k | 4 |

另有 `max_idle_rounds=3`、`tool_timeout_seconds=60`。

**两个容易忽略的点**：

- `tool_call_count` **只计实际执行的调用**，被拒绝的不计（`:191`）。注释写明：预算表达的是"实际做了多少工作"，而且把拒绝计入会让预算自我否定 —— 一轮拒绝一百次就会把下一轮的预算吃掉。
- `max_tokens` 和 `context_budget_tokens` 是**两件事**：前者是整轮累计上限，后者是**单次请求**上限，超了就触发压缩而不是报错。

### 六、上下文层：压缩 + 可召回

`context.py`。触发条件是 `estimate_tokens(messages) > context_budget_tokens`。

**压缩是确定性的，不是调模型总结**。理由：花一次往返做总结本身可能失败，而一个会幻觉的总结比没有总结更糟。

规则：
- 系统提示 + 最近 `keep_recent_messages` 条**永不裁剪**
- 只有超过 `MIN_TRIMMABLE_CHARS=600` 的旧消息才裁，保留头尾
- 裁掉的部分**写入 spill store**，标记里写文件名，`recall_observation` 工具能读回来
- **`recall_observation` 只在 spill 目录存在时才注册** —— 所以标记里承诺的"可读回"永远是真的，不会是空头支票

**这里我第一次写错了，值得记**：固定 head/tail 每次只释放**固定**数量的 token。每轮新增约 950 而压缩释放约 600，于是请求**无界增长，而每一轮都报告"压缩成功"**。实测：

| | 第 8 轮请求大小（预算 3000） |
|---|---|
| 固定裁剪 | **4696 tokens**，仍在涨 |
| 按缺口缩放 | **2420 tokens**；14 轮峰值 2880 |

压到底还压不下去时，报告 `unreachable: true`，**不假装达成了约束**。

token 估算：散文按 4 字符/token，JSON 这类结构化内容按 3（更密），**刻意低估**是安全方向。

### 七、工具层：schema 从签名推导

`@tool` 装饰器 + `build_params_model()`（`tools.py:217`）从函数签名生成 Pydantic 模型，再 `model_json_schema()` 出 OpenAI 格式。

**实测确认**：Pydantic v2 的 `required` 只列没有默认值的字段，所以可选参数真的是可选的 —— 不需要手写 JSON，也就**不会与实现漂移**。

**失败语义全部是"观察结果"而非异常**（`tools.py:95-132`）：

| 情况 | 行为 |
|---|---|
| 工具抛异常 | 捕获 → `ToolResult.failure("RuntimeError: ...")` |
| 参数非法 JSON | 返回 `not valid JSON` + 收到的原文（截断 200 字） |
| 参数 schema 校验失败 | 返回 `invalid arguments` + `errors()` 详情 |
| 工具名不存在 | 返回 `unknown tool 'x'. Available: ...`，**列出可用工具** |
| 工具超时 | `asyncio.wait_for` → `timed out after 60s`（`loop.py:470`） |
| 返回值不可 JSON 序列化 | `default=str` 兜底 |
| 观察结果 > 4000 字符 | 截断 + 标记总长度 |

`ToolRegistry.call()`（`tools.py:199`）的注释直接写了设计理由：*"未知工具作为失败观察返回而不是抛异常，因为模型能从'这个工具不存在'恢复，而循环不能。"*

### 八、委派层：子 agent

`subagent.py`。`spawn_researcher` 工具给子 agent 独立上下文，只回传结论。

- **深度靠 `ToolRegistry.depth` 强制**，默认 `max_depth=1`。到顶时**工具仍然可见，是调用被拒绝并说明原因** —— 藏起来会让模型无法知道"委派存在但已耗尽"，它就永远不会尝试也永远不会解释。
- **子注册表是新建的**，从父表减去委派工具、减去带 `write` 标签的。理由：子 agent 如果能拿到扫描的 `save_prospects`，就是在从父 agent 看不见的上下文里写父 agent 的输出。
- 子 agent 失败**不会中断父 run**。
- 实测子注册表：`['classify_prospect','get_communication_history','get_customer','get_customer_signals','inspect_website','list_customers','search_prospects']` —— 无委派、无写工具、depth=1。

### 九、权限：靠工具不存在

注册表里**没有** `send_*` / `delete_*` / 修改已有客户或邮件记录的工具。基础注册表实测 10 个工具，其中只有两个能写（`create_email_draft` 只存 `pending` 草稿，`upsert_customer` 遇到已存在直接 `skipped`）。

有测试扫整个 agent 包，确认**没有任何 SMTP 引用**。

**边界不靠提示词，靠能力缺失** —— 一条提示词可以被绕过，一个不存在的工具不行。

### 十、和 pi / DSH 的关系

我对照了两个生产级 harness（pi 的 `agent-loop.ts` 源码 + DSH 公开文档），结论有两点：

1. **"有界循环"是我加的，不是抄的。** Pi 的 `runLoop` **没有任何**步数/轮次/token/墙钟上限（源码 grep 零命中）；DSH **明确把"没有轮次预算"写成设计取舍**，留了 `agent/turn-stopping` 钩子给使用者。DSH 自己的 field report 记录了一次 **72 步的单轮**。所以 `AgentBudget` 是两家都留给实现者的那一块。

2. **不变量 1、2 是从它们那儿补上的。** DSH 用 `TOOL_OUTCOME_UNKNOWN` / `TOOL_NOT_STARTED` 保转录配对；Pi 拒绝执行 `stopReason: "length"` 的整批调用。我原本两条都缺。

**刻意没采纳的**：DSH 的四层权限栈（closed approval vocabulary / session `ask`|`never` / per-call sandbox mode / 审计事件不入模型上下文）。它要中介任意文件系统与进程访问；我只需要"不发邮件"，靠注册表里没有这个工具就够了，不需要一个可能出错的策略引擎。

**依据**：`backend/app/agent/` 全部 12 个模块；`AgentBudget` 与三套预设由 REPL 实测打印；子注册表内容实测；对照结论来自 pi 源码（`badlogic/pi-mono` → `packages/agent/src/agent-loop.ts`）与 DSH 公开文档。

**置信度**：
- 分层、状态机、两条不变量、预算数值、压缩算法、工具失败语义、委派深度 —— **从代码读出 + 常量实测打印**
- 压缩缩放前后的 4696 → 2420 对比 —— **实测**（`_probe2.py`，跑完已删）
- pi/DSH 对照 —— **来自子 agent 的调研报告**，它声称读了 `agent-loop.ts` 源码；我**没有亲自复核**那两个仓库
- 真实模型下能跑通（4 轮 / 10 次调用 / 1 次被拒 / 10 秒）—— **实测**（DeepSeek，两次）

**未验证部分**：
- **我没测量过 24k 的 `context_budget_tokens` 和 60k 的 `max_tokens` 是否合理。** DeepSeek 的实际上下文窗口我没查，这两个数是按"够用且不失控"定的，不是按模型能力算的。长时间多轮的真实分布我没有数据。
- **真并发下的行为我不知道。** 单进程跑过，没试过两个 run *同时* 跑。（原本还有一条更严重的：两个 run 先后跑会互相污染委派状态 —— `ToolRegistry` 被就地改写、`spawn_researcher` 闭包绑着上一次运行的记录。这条已修，见 Q2 与提交 `b67024a`，有复现脚本和回归测试。）
- **`max_seconds=300` 的定时任务（`SCHEDULED_BUDGET`）我从来没在 CI 里真跑过。** 我只在本地跑过 180 秒的默认预算。

## Q2. 架构怎么设计的

**答案**：

一句话：**一条 FastAPI 主干，三个入口共用一套有界 agent runtime；AI 调用原本有两套栈，我这次把第二套接到同一个 provider 接缝上。**

### 一、主干

`main.py` 起 FastAPI，lifespan 里做三件事：建表 → 插演示数据 → 起 APScheduler。六个 router 全挂在 `/api/v1` 下。

| 层 | 位置 | 说明 |
|---|---|---|
| 入口层 | `main.py` + `routers/`（6 个） | HTTP；`/scheduler/*` 两个路由直接写在 `main.py` 里 |
| agent runtime | `app/agent/`（12 模块 3757 行） | 见 Q1 |
| legacy AI | `services/agent_service.py`(1093) `services/ai_service.py` `workflows.py`(465) | 关键词分类器 + 直连模型 |
| 共享策略 | `services/follow_up_policy.py`(257) | 阈值唯一来源，两端都用它 |
| 数据层 | `models/` `schemas/` `database.py` | SQLAlchemy async + SQLite |
| 前端 | Vue3 + Vite，dev 代理 `/api` → :8000 | 8 个 view，轨迹用 Mermaid 自渲染 |

依赖方向单向：`routers → services → models`。**唯一一处反向**是 `agent/trade_tools.py:98` 导入 `services/follow_up_policy.py` —— 那是个纯函数模块（没有数据库、没有 IO），放 `services/` 下只是历史位置，它是共享内核而不是上层。

### 二、三个入口，一个 runtime

| 入口 | 路径 | 特点 |
|---|---|---|
| HTTP | `POST /api/v1/agent/run` | **同步**，把整条轨迹一起返回 |
| CLI | `app/cli.py` → `run` / `tools` / `runs` / `show` | 无前端也能跑 |
| 定时 | APScheduler → `workflows.daily_morning_routine` → `find_leads_agentic` | 走 `SCHEDULED_BUDGET` |

三者最后都进 `agent/service.execute()`，落库到 `agent_runs` 表，被 `/agent/runs/{id}/trace.html` 渲染成一张能单独保存的 HTML 页面。

### 三、两套 AI 栈 —— 这是原架构里最大的问题

runtime 那一套是干净的：`agent/protocol.py` 定义规范化消息、工具 schema、`finish_reason` 处理，client 可注入（所以能离线测）。

**但库里另外还有 10 处自己 `AsyncOpenAI(...)`**（`agent_service.py` 8 处、`ai_service.py` 1 处、`workflows.py` 1 处）。实测这 10 处：

- **没有一处传 timeout** → 用的是 openai SDK 默认 **600 秒**
- **没有一处看 `finish_reason`** → 被 `max_tokens` 截断的回答会被当成完整回答
- **有 7 份复制粘贴的 ` ``` ` 剥离**，每份都写 `content.split("```")[1]`，闭括号之后的内容全留着

不是洁癖问题。`max_tokens=300` 用来写一封邮件，截断是常态；截断后的半封邮件会被 `.strip()` 存成 `draft_email` / `rescue_email` 交给用户点发送。

### 四、这次改了什么

1. **`app/llm.py`**：唯一接缝。缓存 client、显式 120s 超时（`OPENAI_TIMEOUT_SECONDS`）、`finish_reason` 命中 token 上限就抛 `LLMTruncated`（**不当成部分文本返回**）、fence 剥离与 JSON 解析各一份。
2. **10 处裸调用 → 0 处**。AST 守卫测试：全库只有 `app/llm.py` 和 `agent/protocol.py` 能构造 provider client、能调 `chat.completions.create`。
3. **如实标注**：`ai_powered` / `fallback_reason`。这两个字段本来就有 —— `analyze_email_reply`、`analyze_inquiry`、`negotiation`、`website`、`churn` 五个函数都带 —— **唯独两个真正写邮件的不带**，其中 `generate_cold_email` 在 key 错、超时、限流时都会静默返回一份硬编码模板。现在三条路径分别报 `no_api_key` / 截断 / 调用失败，前端出徽标。
4. **`scan_leads_draft_workflow` 读的是 `lead["draft_email"]`，而扫描器从来不设这个键** → 那个"AI 生成的草稿"列表里，每一封正文都是内联的一行模板、每一封标题都是同一句 `Partnership Inquiry - X from China`，而 UI 让用户批准并发送。现在真的调 `_generate_lead_draft_email()`。
5. **删掉 `ai_service.analyze_customer_match`** —— 死代码（除测试无人调用），用关键词重叠造一个 0–100 的"匹配分"。项目自己有一条"排序必须是模型判断"的守卫测试，这个函数正好从它的缝里漏过去。

**实测**：真模型（DeepSeek `deepseek-chat`）两条邮件路径都 `ai_powered=True`、无 fallback，5.5 秒；**460 个测试通过，8.4 秒**；前端 `npm run build` 通过。

### 五、还是没做的

- **两套栈仍然并存。** legacy 那 8 个函数还有自己的 prompt 和关键词分类器，没改成工具调用 —— `agent_service.py` 里 `_basic_reply_analysis` / `_basic_inquiry_analysis` / `_basic_analyze_website` 都还在，`test_characterize_classifiers.py` 正钉着它们的现状（包括"no rush 被判 high"那个已知 bug）。
- **`POST /agent/run` 是同步的**，一个 run 最长占住连接 180 秒。
- **真并发没测过**（先后跑会互相污染的问题已修）。

**依据**：`backend/app/` 全树；10 处裸调用与 7 份 fence 剥离由 `Select-String` 计数；`ai_powered` 的分布由 `Select-String` 计数；真模型结果来自 `scripts/smoke_legacy_llm.py` 输出；测试数与耗时来自 `pytest` 末行。

**置信度**：
- 主干分层、依赖方向、三个入口、两套栈、10 处调用、7 份剥离 —— **从代码读出 + 命令计数**
- 「截断的半封邮件会被存成草稿」—— **从代码读出**（`.strip()` 直接赋给 `draft_email`，且没有 `finish_reason` 判断）；**我没有真的造出一次截断来复现**，但 `max_tokens=300` 写一封 100 词英文邮件是紧的
- 「那个草稿列表全是模板」—— **实测**：`scan_runner.py` 构造 lead 时只设 13 个键，不含 `draft_email`，所以 `lead.get("draft_email","")` 恒为空
- 真模型跑通 —— **实测**（DeepSeek，一次）

**未验证部分**：
- 换成 MiMo / OpenAI 官方 endpoint 没验过，只验了 DeepSeek。
- legacy 那 8 个函数在**真实模型下**的截断率我没有数据；我只证明了截断会被正确处理，没证明它多常发生。

## Q3. 这个 agent 的"一次任务"是什么？边界在哪？

**答案**：

一句话：**一次任务 = 一个 goal + 一个 run id + 一个 deadline 的整棵运行树**（父 run 加它派生的所有子 run）。**不是一个 loop** —— 这个区别原来没有落实，下面第三节是我实测出来的漏口。

### 一、任务的起止

- **开始**：有人给出 goal。三个入口（HTTP `POST /agent/run`、CLI、APScheduler 定时扫描）最后都进 `agent/service.execute()`。
- **结束**：五种终态 `succeeded` / `truncated` / `error` / `stalled`（还有运行中的 `running`）。`truncated` 会说明是哪一条预算用尽了。
- **落库**：`agent_runs` 表一行一条，`run_id` 是 uuid4。
- **没有的东西**：没有队列、没有重试、没有跨任务的会话记忆。第二次跑就是第二个任务，除了数据库状态和本次的 spill 目录，什么都不共享。

### 二、七道边界

| 边界 | 值 | 靠什么强制 |
|---|---|---|
| 轮次 | `max_rounds=12` | 在花掉 model 调用**之前**检查 |
| 工具调用 | `max_tool_calls=25` | 超出的**先切分再按声明顺序拒绝**，理由回灌给模型 |
| token | `max_tokens=60k` | 累计，超了 `truncated` |
| 墙钟 | `max_seconds=180` | **整棵树的 deadline**（见第三节） |
| 单轮调用数 | `max_calls_per_round=5` | 超出部分拒绝 |
| 委派深度 | `max_depth=1` | 子注册表构造时就去掉委派工具；到顶时工具仍可见、调用被拒并说明原因 |
| 写权限 | 注册表里**没有** `send_*` / `delete_*` | 只有 2 个写工具，草稿只写 `pending` |

知识边界也在这里：它只知道工具返回过的东西，加上 spill store 里能按名字召回的被裁剪观察结果。

### 三、实测出来的问题：边界原来只画在单个 loop 上

每个 loop 有自己的天花板，而委派会开出新的 loop。父 run 把一轮的开销只在**轮次开始时**记一次账，所以那一轮里派生出去的工作全是免费的。

复现（父预算 1 秒，一轮里两次委派，子预算 10 秒）：

| | 值 |
|---|---|
| 父 `max_seconds` | 1.0 |
| 父 `run.elapsed` | **2.42s**（超 1.42s） |
| 父上报 | 1 次工具调用 / 230 tokens |
| 任务实际 | **3 次工具调用 / 1150 tokens** |

按生产预设放大：`180 + 5 × 90 = 630` 秒，而 `agent_runs.py` 的注释承诺"一个 run 最多占住连接 `max_seconds`"。**注释是假的。**

**修法**：deadline 继承，而不是各自重新计时。

1. loop 算出**一个绝对 deadline**（`start + max_seconds`），已有 deadline 的取更早的那个。
2. 父把 deadline 作为**宿主参数** `_deadline` 传给工具 —— 以下划线开头的参数不进 schema，模型看不见也伪造不了（有测试：模型传 `_deadline=999` 会被忽略，宿主传 `123` 才生效）。**模型能写的 deadline 不是 deadline。**
3. 子 agent 的额度取三者最小：自己 90s、父还剩多少、**父的每次调用上限**。
4. 工具自己的 timeout 按"还剩多少"夹紧，超时消息也改成"运行时间预算用完了"而不是谎报"timed out after 60s"。
5. 一轮里 deadline 过后剩下的调用记为 `run_deadline_reached`，不再执行。
6. 真的被取消时，记录**取消**——原来一个被取消的子 agent 留下的是 `ok=False` + `error=''` + 没有 run，`spawned: 1` 却没有任何解释。

顺带查出的第二个问题：**子 agent 的 90 秒额度落在父的 60 秒每次调用上限后面**，所以它永远在 60 秒被取消，什么都带不回来。现在它拿到较小的那个数，自己停下来并把已经查到的结果交回（留 0.25s 收尾余量，常量 `DEFAULT_UNWIND_SECONDS`）。

### 四、账目：父的计数看不见子 agent 的工作

这是"边界在哪"的另一半。同一个任务，父的计数器只报自己的。现在：

- `service.summarise()` 同时给 `tool_calls`（父）和 `tool_calls_total` / `tokens_total` / `delegations`（任务）
- `GET/POST /agent/run` 的响应模型加上这几个字段（不加的话 FastAPI 会直接丢掉）
- trace 页表头在发生委派时多一行："sub-agents：N（不计入以上数字）"

真模型实测（`scripts/smoke_delegation.py`，DeepSeek）：一个子 agent 跑了 **5 次工具调用 / 7730 tokens / 21.3s**，返回了带证据的答案，而父自身的计数是 0 —— 正是这些数字原来会消失的地方。

### 五、刻意不做的边界

- **`POST /agent/run` 仍然是同步的**，一个任务会占住连接直到 deadline。
- **`agent_runs` 表没有委派相关列**，所以列表页的数字仍然是父 loop 的。加列需要迁移，而本项目只有 `create_all()`（它不会 `ALTER TABLE`），给现有库加列会让运行中的实例炸掉 —— 这是明确的取舍，不是漏掉。
- 没有并发上限。子 agent 是串行的（一次一个），但两个 `POST /agent/run` 会各自跑。

**依据**：`backend/app/agent/loop.py`、`subagent.py`、`tools.py`、`service.py`、`render.py`；超时数值来自 `_probe_boundary.py` 的输出（临时探针，跑完已删，同样的场景现在由 `tests/test_agent_task_boundary.py` 12 个测试覆盖）；真模型数字来自 `scripts/smoke_delegation.py`；测试 472 个通过（9.8 秒）。

**置信度**：
- 起止、七道边界、五种终态、没有队列/重试/记忆 —— **从代码读出**
- 2.42s 超时、1 vs 3 次调用、230 vs 1150 tokens —— **实测**（探针）
- 630 秒最坏值 —— **算术**：同一个组合规则套生产预设，我没有按 630 秒真跑过
- 91 行那个"子 agent 被父的调用上限取消" —— **实测**（探针日志里 `delegation.error=''`、`run=None`）
- 真模型委派跑通 —— **实测**（DeepSeek，一次）

**未验证部分**：
- **真并发没测过。** 两个 `POST /agent/run` 同时打进来会怎样，我没有数据。先后跑会互相污染的问题已经在 `b67024a` 修掉。
- **`DEFAULT_UNWIND_SECONDS = 0.25` 是我定的，不是量出来的。** 它只需要大于"子 agent 从时间检查到返回"的开销，我没有测过那个开销的真实分布。
- **630 秒那一档没有跑过**，只跑了 1 秒和 0.3 秒量级的探针。

## Q4. 客户先回了你第 3 封邮件，前两封还没回 —— 状态机怎么表达？

**答案**：

**原来表达不了，而且它说的是反话。** 现在能表达了，表达方式是：**一个会话（thread），不是三个消息。**

### 一、原来的状态机长什么样

- `EmailLog.status`：`pending → sent → delivered → opened → replied`，还有 `bounced` / `failed`。**一条出站记录一个状态。**
- `EmailLog.replied_at`：这一封的回复时间。
- `Customer.stage`：`new / contacted / interested / quoting / completed / lost`。
- 没有的东西：**没有方向**（`email_logs` 只存我们自己发出去的，没有任何地方能存一封收进来的信）、**没有 thread id**、**没有 `in_reply_to`**、**没有序号**。

### 二、两个实测出来的硬伤

**硬伤 1：`REPLIED` 这个状态进不去。** 全库只有三条状态转换被实现：`PENDING → SENT|FAILED`（发送）、`SENT → OPENED`（追踪像素）。`PUT /emails/logs/{id}` 只能改 subject/body/to_email。**没有任何 endpoint、workflow 或 agent 工具写过 `replied_at` 或 `status=replied`。**

后果不是"少个功能"，是**好几个数字在撒谎**：

- `/emails/stats` 的 `reply_rate = total_replied / total_sent` —— 分子恒为 0，所以**这个比率按构造永远是 0.0%**。
- `ChurnPolicy.no_reply_critical_emails = 3`：**凡是发过 3 封的客户一律 critical**，理由"Sent 3 emails, received 0 replies"，因为回复记不下来。
- agent 的 `get_customer_signals` 对每个客户都报 `has_any_reply: false`，永远。

**硬伤 2：账算在了消息上，而不是会话上。** 就算回复记下来了，`assess_churn` 数的是"发过几封、几封被回复"，`assess_follow_up` 则**完全不看回复**，只看"距上一封多久"。实测：

| 读法 | 结果 |
|---|---|
| 今天（回复记不下来） | `critical`：**"Sent 3 emails, received 0 replies"** → 建议"换个渠道试试（WhatsApp/电话）" |
| 假如回复记下来了 | `None`：**毫无风险** |

两个答案都是错的。而 follow-up 列表对同一个客户给的是：

```
('high', 'No reply in 8 days', 'Send a follow-up email with different angle')
```

—— 对一个两天前刚回信的客户说"8 天没回复，换个角度再追一封"。

### 三、正确的模型：会话，不是消息

一次回复是**会话上的事件**，不是某一条消息的属性。该问的从来不是"第 2 封被回复了吗"，而是**"谁最后说话，谁欠谁一个回复"**。三件事随之改变：

1. **在第一次回复之前发出去的信是"被越过（superseded）"，不是"被无视"。** 客户回了第 3 封，不等于他无视了前两封 —— 会话往前走了。追着问第 1 封是噪音。
2. **最后一次回复之后发出去的信才是"在等回复（awaiting_reply）"。** 这才是 "no reply" 规则该数的东西。
3. **如果会话里最新的是"他们"的信，那沉默的是我们。** 这一条原来的规则**完全看不见**：它数出站行、看出站时间戳，所以昨天刚回信的客户读起来是"发了 3 封，0 回复"。

### 四、改了什么

1. **`derive_thread_state(emails, now)`**（`follow_up_policy.py`，纯函数）：从出站行里推出 `outbound / superseded / awaiting_reply / answered / they_wrote_last / reply_owed_days`，以及两个时间戳。这是整个答案的核心。
   - 判定"被回复"看 `replied_at`，**不看 status** —— 时间戳是事实，枚举是记账，现实里两者会不一致（有测试）。
   - `bounced` / `failed` 不算 outbound：没送达的信不在等回复。

2. **补上唯一缺失的写路径**：`POST /api/v1/emails/logs/{email_id}/reply`。
   - **幂等**：同一条再记一次不会移动时间戳（"回复发生过一次"）。
   - **不改 stage**：回复是接触，不是阶段跃迁；系统自作主张把 `contacted` 改成 `interested` 是另一个猜测装成事实。
   - 拒绝：未送达的信（409，"一封没发出去的信不可能被回复"）、未来时间（422）、**早于发信时间的回复（422）** —— 后者会让整个推导变成胡话（所有信都显得在回复之后发出，于是没有一封在等回复，会话读起来像已结案）。
   - 记完返回推导出来的会话状态，调用方立刻能看到效果。

3. **规则改成读会话**：
   - `assess_churn` 新增规则 0：`they_wrote_last` → 按 `reply_owed_critical_after_days=2` 升级为 critical，理由"Customer replied 2 day(s) ago and has not heard back"，动作"Answer their message. They wrote last, so the delay is ours."；"no reply" 规则改数 `awaiting_reply`。
   - `assess_follow_up`：`they_wrote_last` **排在 quoting/interested 之前**（这不是程度问题，是唯一一个下一步动作没有歧义的）；已回复且不欠回复 → "Conversation answered N day(s) ago; waiting on them"，**不再出现 "No reply in N days"**。
   - 两个函数都保留 `thread=None` 的旧行为，好让边界测试一次只验一条规则；**但生产里没有任何调用点可以不传** —— 有 AST 守卫测试盯这一点（我临时删掉一处 `thread=thread` 验证过它真会红）。

4. **agent 侧** `get_customer_assessment` 多返回 `conversation` 块和 `emails_awaiting_reply` / `emails_superseded_by_a_reply` / `they_wrote_last`，`note` 里明说"读数字之前先读 conversation"。churn / follow-up 两个接口的返回里也带上 `conversation`。

5. **前端** `/emails` 的日志表加了一列"Mark replied"（只有 sent/opened/delivered 才出现），点了会告诉你"你欠他们一个回复"。没有这个按钮，新状态在界面上仍然进不去。

**实测**（HTTP 全链路，`tests/test_reply_endpoint.py`）：给同一客户发 3 封 → 第 3 封记回复 →
`outbound=3, superseded=2, awaiting_reply=0, they_wrote_last=True`；前两封仍然是 `sent`（没有被抹掉）；follow-up 那条从"Recently contacted, wait for reply"变成 **"They replied 0 day(s) ago and have not heard back" + "Answer their message"**；再点一次不移动时间戳；`total_replied` 不再是 0。

**498 个测试通过**（原 472），10.3 秒；前端 build 通过。

### 五、还没做的部分

- **没有入站消息表。** 回复仍只是出站行上的一个时间戳：存不下"他们说了什么"，也存不下"这封回的是哪一封"（`in_reply_to`）。要真正做对话，需要一张 `email_messages` 表（方向 + message_id + 线程），而**加列是不可能的**：`init_db()` 只 `create_all()`，不会 `ALTER TABLE`，给运行中的库加列会炸。**加表是安全的**（`create_all` 会建缺失的表），所以这是下一步该走的路，不是可以顺手改的。
- **回复内容不进 agent 的上下文。** agent 能看到"他们回了"，看不到回了什么。`analyze_email_reply` 是独立的接口，要人把邮件正文粘进去。

**依据**：`app/models/email_log.py`、`app/routers/emails.py`、`app/services/follow_up_policy.py`、`app/services/agent_service.py`、`app/agent/trade_tools.py`；"没有任何写路径"由 `Select-String` 全库扫描确认（`replied_at =` 与 `status = EmailStatus.REPLIED` 在改动前 0 命中）；两种错误读法由命令行实测打印；HTTP 全链路结果来自 `tests/test_reply_endpoint.py`。

**置信度**：
- 三条状态转换、没有方向/线程/序号、`reply_rate` 恒为 0 —— **从代码读出 + 全库扫描**
- 表格里那两种错误读法、以及 "No reply in 8 days" —— **实测**
- 新模型对场景的读数 —— **实测**（纯函数 + HTTP 两层）
- "加列会炸" —— **从代码读出**（`init_db()` 只有 `create_all()`）；我没有拿一个旧库真的试过

**未验证部分**：
- **真实的 SMTP 往返没测过。** 测试里发送是模拟的（没有 SMTP 凭据），所以"发送成功后状态是 sent"是模拟路径。真发信走的是另一支。
- **没有真实客户数据。** 演示库里所有客户的 `email_logs` 都是空的（这也是之前那次真模型运行发现"notes 说联系过、日志说没联系过"的原因）。所以"superseded 会有几个"只有构造的数据。
- **`reply_owed_critical_after_days = 2` 是我定的**，不是从数据里量出来的。它是一个观点，现在至少是一个**有名字、能改、有边界测试**的观点。

## Q5. 跟进计划怎么设计？—— 主动 agent 的核心

**答案**：

**跟进计划不是"今天谁看起来急"的报告，是每个客户一条承诺：下一个动作 + 什么时候到期。** 原来的实现是前者。实测：同一个客户的条目，连续三次调用**逐字节相同**，没有到期时间，没有"这是第几次"。

### 一、原来是什么

`daily_follow_up_intelligence()`：遍历在跑的客户 → `assess_follow_up` → 排序 → 给前 5 个生成草稿。每次调用都从零重算。

三个证据说明它是查询不是计划：

1. 三次调用输出**逐字节相同**，且不含 `due` 和 `attempt`。
2. **`Customer.next_follow_up_at` 这个列，从项目存在到现在没有被写入过任何值。** 为"下次什么时候跟进"准备的字段一直在，这个概念不在。（上一轮我在回复接口里写过一次 `None`，那是清空。）
3. `Task` 表有 `due_date` / `status` / `task_type='follow_up'`，跟进计划**从来不创建任务**。

查询的答案不变，所以它每天早上说同一件事，直到天荒地老 —— 这是"主动"和"复读"的区别所在。

### 二、计划要回答四个问题，每个对应一个字段

| 问题 | 答案放在哪 | 原来的状态 |
|---|---|---|
| 什么时候做 | `due_at`，并写回 `next_follow_up_at` | 没有这个概念 |
| 这是第几次 | `attempt` = 客户上次说话之后我们发了几封 | 没有 |
| 什么时候停 | `kind`：到上限换成 change_channel，再往后 review | 没有，会一直追 |
| 什么取消它 | 回复 / 发送失败 / 关单 | 只有部分 |

### 三、动作词表（封闭，5 个）

`answer_them` / `fix_delivery` / `send_follow_up` / `change_channel` / `review`

**第一版我写了第 6 个 `keep_momentum`，探针证明没有任何可达状态能产生它**（能产生它的路径都被上面的规则先接住了），于是删掉。给词表加一个状态产生不出来的词，就是把词表变成装饰。现在有一个测试断言**每个声明的 kind 都有构造出的状态能产生它**。

### 四、调度算术

- 第一次跟进：我们发信 + 3 天
- 第 n 次：发信 + `3 + 3×(n-1)` 天 —— **退避**。无视了两封邮件的人不想明天收到第三封。
- 到 `max_attempts=3`：`change_channel`，到期时间按同样的退避算，但**动作不再是邮件**（有测试断言这个 kind 不会带出草稿）
- 超过：`review`，再 +60 天 —— 停手，但不忘
- 每天上限 20 条，**超出部分计数上报**（`deferred`）：被截断的列表会被读成完整的列表

优先级不再是"quoting 永远 high"，而是**到期才算**：今天上午发出去的报价，今天不出现。

### 五、幂等与增量 —— 这里有个我自己写错又被测试抓到的 bug

计划有两个列表，因为它们回答两个不同的问题：

- `commitments`：每个客户一条，**全部**（调度写成 `next_follow_up_at`）
- `actions`：**今天到期的**，排序 + 上限（调度任务今天做的事）

第一版我**先按 due 过滤再持久化**，于是"排到未来"的那些决定**从来没被写下来** —— 而那正是让明天变得增量的东西。过滤只作用于今天要做的事，不作用于承诺。

### 六、实测（同一套演示数据）

| | 结果 |
|---|---|
| 完整队列 | `#4` attempt=3 → `change_channel`，到期 10-25 |
| day 1，仅到期 | `#4` **不在列表里** |
| day 2，仅到期 | `#4` **仍然不在** —— 决定被写下，不是被重算 |
| 每天都出现 | `#1`/`#2`：stage 有、email 一条没有，今天确实欠着 |

**重复一个逾期项不是 bug，重复一个已经排到期未来的项才是。** 这是两种"每天出现"的区别，也是这个模块存在的理由。

### 七、agent 侧

新工具 `get_follow_up_plan`（只读，`persist=False`）：**调度器负责提交，agent 负责读计划和解释**。工具告诉模型 kind 是封闭词表、attempt 是什么，并明说"你不同意某条就说出来并给理由"。

分工是刻意的：**排期是算术，判断才是模型的事**。让语言模型决定"三天后还是四天后"既不可复现也不值得花钱。

### 八、还没做的

- **计划不创建 `Task` 行。** 表已经在那里，但自动取消人手工建的任务是我给不了的承诺；`next_follow_up_at` 已经承载了承诺本身。
- **没有"上次已经提醒过你"的状态。** 逾期项每天都会出现（这是对的，它确实到期了），但通知不做去重。要做需要一个 `last_surfaced_at` 字段 —— 新列，而**加列在这个项目里不可能**（`init_db()` 只有 `create_all()`），所以这也要走"加表"那条路。
- **时区完全没有处理。** 全部 `datetime.utcnow()`，"每天早 6 点"是 APScheduler 的 cron。给德国客户和给日本客户"今天发信"是同一个今天。
- **`max_actions_per_day=20`、退避 `3/3`、`max_attempts=3`、`parked_review_after_days=60` 都是我定的**，不是量出来的。

**依据**：`app/services/follow_up_plan.py`（新）、`app/services/agent_service.py`、`app/agent/trade_tools.py`、`app/workflows.py`、`app/routers/agent.py`；"三次逐字节相同"与"`next_follow_up_at` 从未被写入"由全库扫描 + 探针实测；第六节的表格来自探针输出（跑完已删，同样的场景由 `tests/test_follow_up_plan.py` 25 个测试覆盖）；**523 个测试通过**（原 498），连跑三遍稳定。

**置信度**：
- "原来没有 due/attempt、三次输出相同" —— **实测**
- "`next_follow_up_at` 从未被写入" —— **全库扫描**（改动前 `next_follow_up_at =` 只有我上一轮的 `= None`）
- 所有 kind 都可达 —— **探针 + 测试**（第一版的第 6 个 kind 就是被这个探针否掉的）
- 幂等/增量、退避、上限、取消 —— **实测**（纯函数 + HTTP 两层）
- "先过滤再持久化"那个 bug —— **测试抓到**，不是我看出来的

**未验证部分**：
- **没有任何真实客户数据。** 演示库里所有客户的 `email_logs` 都是空的，所以"一个客户被追到第 3 次"这件事在真实数据里发生频率多高，我没有数据。
- **退避曲线没调过。** 3/3 是我按"第一次 3 天、之后每次多等 3 天"定的，没有打开率/回复率数据支撑。
- **20 条/天的上限没在真实量级上试过**（演示库里在跑的客户只有 3 个）。

## Q6. 100 个客户同时跟，怎么保证不串？

**答案**：

先把并发模型说清楚，因为它决定了"不串"是什么意思：**一个进程、一个事件循环、一个 SQLite 文件**（`start.bat` 是 `uvicorn --reload`，没有 `--workers`），每个请求一个 session。100 个客户不是吞吐问题 —— 计划是同一套算术。**先坏的是重叠**：两件事同时碰同一批行。

### 一、查过了：数据路径上没有共享的可变状态

- 每个请求自己的 session（`get_db` 的 `async_session()`）
- 每个 agent run 自己的 registry 副本、委派记录、spill 子目录（前几轮修的）
- 每次扫描自己的 `ProspectSink` 和 registry（`scan_runner` 每次调用新建）
- 全库模块级可变状态只有三处：`llm._client` 缓存、`scheduler._scheduler`、以及这次新加的锁 —— 前两个是刻意的

所以"串"**不来自状态共享**。这一点值得先说，否则会去修一个不存在的问题。

### 二、真正会串的是重叠：实测

`POST /emails/send-pending` 和 `/send-pending/{id}` 都是 **read → `await send_email(...)` → write**。中间什么都没占住，窗口是整次 SMTP 往返那么宽；而 `status == PENDING` 的检查在 `await` **之前**，所以它什么都没保护。

**观察到一次**：10 个草稿、两次并发调用 → **20 次 SMTP 调用**，每个客户收到同一封邮件两遍。而两次调用都报 `sent=10`、所有行最后都是 `sent` —— **重复在记录里不留任何痕迹**。

**诚实说明**：这个观测**不能按需复现**。第二次调用的读是否落在第一次的发送窗口内取决于调度。但**机制是无条件的**：读和写之间没有任何 claim。我又试了三四次都没复现，所以测试里我断言的是**不变量**（每个草稿最多发一次、恰好一个调用被拒），不是某一种交错。

### 三、修法：拒绝，而不是排队

`_exclusive_send`（非阻塞获取）+ **在锁内重新读**。第二次调用拿到 **409**，而不是排队等一整批 —— 100 个客户的一批是几分钟。单发和批量共用同一把锁，否则批量会发掉单发正在发的那封。

**不用 "sending" 状态**：发送前置位、发送后清除的状态，在进程中途死掉时就是谎话（行说"已发"，实际没发），而且会把行永久卡在中间。**数据库保持诚实**：`status` 只在发送真的发生之后才变。

### 四、顺手修掉两个更根本的问题

**1. `asyncio.Lock` 绑定事件循环 —— 这是我第一版被测试打出来的。**

第一版我用模块级 `asyncio.Lock` + `locked()` 检查。它能工作，直到另一个事件循环来争用：`RuntimeError: <Lock ...> is bound to a different event loop`；更糟的是它**静默地**让 plan run 被 skip（`locked()` 返回 True 就直接返回 skipped）。生产里只有一个循环所以看不见，其它任何地方都是陷阱。

换成 `threading.Lock.acquire(blocking=False)`：**原子的 test-and-set**（检查和获取之间没有缝，比 `locked()` + acquire 更强）、**不阻塞事件循环**、**没有循环亲和性**。

**2. N+1 → 3 次查询。**

计划和 churn 任务原本每个客户 2 次查询（邮件 + 联系人）：100 个客户 = 300+ 次往返挤在一个事务里 —— 慢，而且在 SQLite 上是一个很长的窗口，另一个定时任务会撞上锁。现在整本书 3 次查询。

**结果按 customer id 分组，绝不按位置对齐。** 用两个结果列表按下标配对，就是一个客户的历史进到另一个客户计划里的方式 —— 这是"串"的经典形状，所以在测试里明写出来。

### 五、测试（`tests/test_concurrency_isolation.py`，10 个）

| 断言 | 怎么测 |
|---|---|
| 100 个客户，每个只用**自己的**历史 | 100 个互不相同的历史（长度 + 是否回复都不同），断言每条 `attempt` / `evidence` / 联系人都只对应自己的输入 |
| 每个客户恰好一条承诺 | 100 条 commitments，按 id 去重 |
| 顺序与到达顺序无关 | 正着读、反着读，`as_dict()` 逐字节相同 |
| 批量读按 id 分键 | SQL 监听器断言 `email_logs` 和 `customer_contacts` **各只被查一次** |
| 两个并发批量发送 | ≤10 次 SMTP、恰好一个 409（用闸门卡住窗口，不靠运气） |
| 批量 + 单发不能重叠 | 同一封草稿不会被发两次 |
| HTTP 层 | 200 + 409 |
| 读计划不拿锁 | 把仪表盘挡在慢写后面，是仪表盘开始超时的原因 |
| 第二个提交型 plan run | 被 skip，不是被重算 |

**把锁去掉验证过**：发送锁 → 3 个测试红；计划锁 → 1 个红。

### 六、同一次里还发现一个测试隔离的坑

我在新测试文件里创建了 session 数据库的第一批客户 → `_insert_demo_data()` 只在**客户表为空**时播种 → 之后所有依赖演示数据的文件全部 `customer 4 not found`。**pytest 的文件收集顺序决定了测试是否通过**，而单独跑每个文件都是绿的。

修法：把播种挪进 `conftest` 的 session fixture（和建表在一起），不再依赖"哪个文件先跑"。这不是产品 bug，但它和这个问题属于同一类：**共享资源 + 隐式顺序**。

### 七、诚实的天花板

- **锁是进程内的。** `uvicorn --workers 2` 就破了：两个 worker 各有各的锁，各自都能发同一批。那时需要数据库里的 claim 行（`UPDATE ... WHERE status='pending'` 抢占用 affected-rows 判定）。**现在没有。**
- **发送没有跨崩溃的恰好一次语义。** 进程在发送中途死掉：邮件可能发出去了，行还是 `pending` → 下一批会再发一次。真正解决需要持久化 outbox + SMTP 侧的幂等键。
- **SQLite 的写是进程级串行。** 100 个客户同时跑 agent 循环会互相等。我**没有做压测**，也没有量出 "database is locked" 的出现率。
- **没有全局的并发 agent run 上限。** 100 个 `POST /agent/run` 就是 100 个循环，谁都拦不住。

**依据**：`app/routers/emails.py`、`app/services/agent_service.py`、`app/database.py`、`app/agent/scan_runner.py`、`start.bat`；"20 次 SMTP 调用"由 `_probe_race.py` 观察一次（探针跑完已删，同样的形状由 `tests/test_concurrency_isolation.py` 覆盖）；循环亲和性的报错和锁的失效验证都是实测；**533 个测试通过**（原 523），连跑三遍稳定。

**置信度**：
- 并发模型（单进程、每请求一 session、SQLite）、没有共享可变状态 —— **从代码读出**
- 读-await-写之间没有 claim —— **从代码读出**，且是机制性的
- "20 次 SMTP 调用" —— **观察到一次，不能按需复现**。这是本条里我最想把话说准的一处：现象是真实的，可复现性不是
- `asyncio.Lock` 的循环亲和性 —— **实测**（不是读文档得出的）
- N+1 → 3 次查询 —— **实测**（SQL 监听器计数）
- 去掉锁测试就红 —— **实测**

**未验证部分**：
- **没有压测。** "100 个客户"是我按代码推算的形状，不是跑出来的负载。SQLite 写锁在真实并发下的失败率我没有数据。
- **多 worker 的行为只是推断。** 我没有真的起过 `--workers 2`，所以"锁会失效"是从"锁是进程内的"推出来的，不是测出来的。
- **测试隔离的坑我只在这两个文件上验过**（`test_concurrency_isolation.py` + `test_follow_up_plan.py` + `test_reply_endpoint.py` 一起跑绿）。全量套件三遍绿，但我没有穷举所有文件组合。

## Q7. 人在环路：AI 建议了但要人确认，状态怎么挂起？

**答案**：

这个系统里唯一"挂起"的地方就是 **`EmailStatus.PENDING`** —— 草稿写好了、等人决定。它原来有两个问题：**对计划不可见**，而且**否决等于删除**。

### 一、原来：挂起这个状态在系统里不存在

- 唯一的人环闸门就是 `pending` 草稿 + 人按 Send。写入方是 agent 的 `create_email_draft`、扫描导入、以及人自己。
- 但 `pending` 不是"挂起"，它只是**一行还没发出的邮件**：
  - **计划看不见它。** 实测（10 天前发过一封邮件）：

    | | kind | due | reason |
    |---|---|---|---|
    | 有一封待批草稿 | `send_follow_up` | 2026-10-09 | "No answer to 1 email(s)" |
    | 没有任何草稿 | `send_follow_up` | 2026-10-09 | "No answer to 1 email(s)" |

    **逐字节相同。** 所以每天的清单会让人去追一个"邮件已经写好、正卡在他自己审批队列里"的客户。
  - `POST /emails/send-pending` 一键把**所有** pending 全发出去 —— 复核过的和没复核过的一起走。
- **否决 = 删除**：`DELETE /emails/logs/{id}` 把行删掉，什么都没记下，下一轮 agent 又会提同样的建议。

### 二、修法：把"等人"变成一个状态

新增 kind **`awaiting_approval`**（词表现在 6 个，每个都能被某个可达状态产生，有测试盯着）：

- `due_at` = 最早那封草稿的时间 + `approval_reminder_after_days=2` → **新鲜时不算到期**
- **排在所有规则之前，包括 `they_wrote_last`** —— 因为那封待批的草稿很可能就是给他的回复
- 但它**不抹掉紧迫性**：理由同时写两件事 ——
  `1 draft(s) waiting for your approval (oldest 0 day(s)); they replied 2 day(s) ago`
- 它**不在 `EMAILING_KINDS` 里** → 不会为一个待批建议再生成一个建议草稿（"对建议的建议"不是个东西）
- 排期任务今天不列它（实测 `in today's due list: False`）
- 超过提醒窗口 → 升级 `high`，理由变成**提醒人**，而不是催客户

### 三、否决要被记住

- 新增 `EmailStatus.REJECTED`。**加枚举成员对老库是安全的**：我实测了新库的 DDL —— `status VARCHAR(9)`，**没有 CHECK 约束**，而且 SQLAlchemy 存的是枚举的 *name* 不是 value。所以不需要改表。
- `POST /emails/logs/{id}/reject`：幂等、已发出的不能否决（409）、**行保留**。
- 否决理由存进 `error_message`。**这个字段名叫 error_message，把否决理由放进去是在借用它的名字 —— 我借用了，并在这里说明**：加列在这个项目里做不到（`init_db()` 只有 `create_all()`，不会 ALTER），而理由不记下来就等于又丢一次信息。
- `DELETE` 保留：删掉自己写的草稿是正当的；**否决是一次决定**，删掉就什么都不剩。
- 否决之后计划照样说话，而且说实话：`send_follow_up` + "1 proposal(s) rejected; nothing has been sent to this customer" —— 这和"没有任何邮件记录"是两回事，原来的规则分不出来。

### 四、实测（HTTP 全链路，`tests/test_approval_gate.py`，11 个）

| 断言 | 结果 |
|---|---|
| 待批草稿 → 挂起 | `awaiting_approval`，`due_in_days > 0`，**不在今天的到期列表里** |
| 放了 5 天 | 出现在到期列表，priority `high`，"oldest 5 day(s)" |
| 发送草稿 | 挂起结束（`pending_proposals == 0`） |
| 否决 | 200，行还在，`status=rejected`，`rejected_proposals == 1` |
| 再否决一次 | `already_rejected: true`，理由仍是第一次的 |
| 已发出的草稿 | 否决被拒（409）；未知 id 404 |
| **被否决的草稿不会被 `send-pending` 发出去** | 断言那个地址没被发 |
| 否决之后 | 客户仍在计划里，理由说明"被否决过" |

### 五、顺带查出：仓库里有三个文件是坏的，而且没有任何东西会报

`git ls-files --eol` 显示 `backend/app/models/` 下三个文件是 **`i/-text w/-text`** —— git 认为它们是**二进制**。原因：每一行都以 `\r\r\n` 结尾（一个把 `\n` 变成 `\r\n` 的 shell，在已有的 `\r\n` 上又做了一遍）。

四件事同时为真，所以谁都没发现：

- git 认为是二进制 → **永远不会规范化**
- 工作区和 blob 逐字节相同 → **`git status` 说它干净**
- 行尾测试只检查 `i/lf` 的文件 → **测不到它**
- Python 不在乎 `\r\r\n` → **跑得好好的**

修法：`scripts/repair_line_endings.py` 只改行尾（实测 4669→4455、2013→1911、1157→1109 字节），重新 add 之后 git 恢复成 `i/lf w/lf`。再加两个测试：**git 认成二进制的文本文件必须报错**、**任何文件不允许出现 `\r\r\n`**。

这是我这轮自己踩出来的：我本来想用同一种 shell 方式改 `email_log.py`，把同样的损坏又做了一遍，然后发现 `git checkout` 修不回来（git 认为文件没变），才顺着查到了这三个文件。

### 六、还没做的

- **没有真正的审批队列。** 待批项分散在 `/emails/logs` 和计划里，没有一个端点把"哪个 agent 提的、为什么、证据是什么"放在一起。现在拼得出来，但没有一个地方看。
- **计划和草稿之间没有外键。** 计划知道"这个客户有草稿待批"，但不知道是**哪一封**，也不知道那封是不是针对客户最新回信的。所以 `awaiting_approval` 的理由只能并列陈述两件事，**不能断言"这封草稿就是那封回复"**。
- **`error_message` 装否决理由是借名。** 真正的修法是加一列或加一张 `proposal_decisions` 表；**加表安全**（`create_all` 会建缺失的表），加列不安全。
- **没有多步审批，也没有超时过期。** 一封放了半年的草稿仍然是"待批"，不会被自动作废。

**依据**：`app/models/email_log.py`、`app/routers/emails.py`、`app/services/follow_up_plan.py`、`app/services/follow_up_policy.py`、`app/workflows.py`、`app/agent/trade_tools.py`；"逐字节相同"和"不在到期列表"由探针实测（跑完已删，同样的场景由测试覆盖）；枚举 DDL 无 CHECK 约束是**实测**（打印 `sqlite_master.sql`）；行尾损坏由 `git ls-files --eol` 与字节统计共同确认；**550 个测试通过**（原 533），前端 build 通过。

**置信度**：
- "计划看不见待批草稿" —— **实测**（两种情况输出完全一致）
- "否决等于删除、没有记录" —— **从代码读出**
- 加枚举成员对老库安全 —— **实测 DDL**；但我**没有拿一个真实的老 `.db` 文件试过**
- 行尾三文件损坏及修复 —— **实测**（字节级前后对比 + `git ls-files --eol` 变化）
- 挂起/提醒/否决/幂等/不发被否决的草稿 —— **实测**（HTTP 层 11 个测试）

**未验证部分**：
- **没有真实的多用户/多 agent 场景。** "哪个 agent 提的"目前根本不存在于数据里（没有 provenance 列），所以我没有测试过两个 agent 对同一客户各提一稿会发生什么。
- **提醒窗口 2 天是我定的**，不是量出来的。
- **老数据库迁移只是推断。** 我验证了 DDL 里没有 CHECK 约束，但没有真的拿一个已经存在的库跑过 `init_db()` + 新枚举。
- **前端我只验证了能 build**，没有在浏览器里点过 Reject 按钮。

## Q8. 深度分析要跑 3 分钟，不能阻塞整个流程，怎么办？

**答案**：

这里有**两个独立的阻塞**，必须分别解，而且第二个比第一个严重：

1. **调用方被挂住** —— `POST /agent/run` 一直握着连接不放。
2. **整个进程被冻住** —— 真正做"深度阅读"的工具是 `async def`，函数体里却全是同步阻塞 I/O。

只解第一个没用：把调用方挪到后台，进程照样是死的，health check、页面请求、定时任务全部停摆。

### 一、实测：一次分析让整个进程停摆 2950 ms

工具跑 3 个页面、每个 1 秒阻塞 I/O。测法：起分析 → 让事件循环 50 ms 后叫醒我 → 看实际迟到多久。

| | 墙钟 | 其它工作被推迟 |
|---|---|---|
| 阻塞调用直接在 async 工具里 | 3.00s | **2950 ms** |
| 同样的工作放到 worker 线程 | 3.02s | **12 ms** |

**3 秒的分析里有 2.95 秒，这个进程谁都别想动。** 真实工具用的是 `requests.get(timeout=15)`，所以最坏是每页 15 秒 —— 十个页面就是 150 秒整个应用无响应。

### 二、修法一：把阻塞挪到线程

`inspect_website` 的抓取**和解析**、`search_prospects` 的搜索、`analyze_customer_website` 的抓取 → `asyncio.to_thread`。墙钟不变，进程不再停摆。实测（真实工具 + 慢速 fetch）：3.05s 墙钟，**其它工作推迟 13 ms**。

### 三、修法二：调用方不再等

- `POST /agent/run` 默认 **`wait=false`**：写一行 run 记录 → 立刻返回 **202 + run_id + poll URL**，分析在后台跑。
- `wait=true` 保留原来的同步形状（CLI、短任务、测试用）。
- **`run` 行在开工前就写。** 原来的注释写着"the storage for that already exists, so the change is additive" —— **那句话是假的**：行只在 run *结束*时才写，所以"排队+轮询"在整整 3 分钟里拿到的是 404。
- **进度**：每轮结束通过 `on_step` 把 rounds/trace 写回。轮询能看到它在动 —— 否则"没有输出"分不清是慢还是死了。
- **失败要落地**：后台任务抛异常 → 该行标成 `error`，绝不留在 `running`。
- **有上限**：同时最多 3 个，超过返回 **429** 而不是排队 —— 无界队列是看不见的积压。
- **崩溃与关停**：关停时 drain（最多等 5 秒）；进程死掉留下的 `running` 行，下次启动由 `mark_stale_runs` 标成 `error`（否则轮询者永远在等一个不会来的答案）。
- SQLite busy timeout 5s → 30s：长分析现在会在服务请求的同时写进度，而 SQLite 一次只让一个写者进。

### 四、顺带查出：`inspect_website` 这个工具从来就跑不起来 —— 而且死了两次

这是本轮最重的发现，而且**只有先把 `requests` 装上才会暴露**：

1. **`requests` 声明在 `backend/requirements.txt` 里，但虚拟环境里没装。** 所以 `import requests` 直接失败，工具每次返回 `ModuleNotFoundError` 观察结果（`ddgs` 同样）。
2. **`_extract_emails` / `_extract_phones` 被调用但从未定义。** 装上 `requests` 之后，第一次成功抓取就 `NameError`。

两个都是"看起来实现了、实际跑不了"。**测试抓不到的原因是：所有走扫描路径的测试都把这两个工具替换成了罐头响应**（`scan_stubs`）—— 函数体一次都没被执行过。

我做了：装上这两个已声明的依赖；补上两个缺失的函数（含垃圾邮箱过滤 —— CSS 里的 `sprite@2x.png` 完全符合邮箱正则 —— 以及按位数过滤电话号码）；加了一组测试：依赖必须可导入、抽取函数有用例、`inspect_website` **端到端**跑一遍（patch 掉网络）。最后这个用例在旧代码上会红，而且是唯一能同时抓到那两个缺陷的用例。

**571 个测试通过**（原 550）。实测真实抓取 `https://example.com`：`status_code=200`，标题、正文都解析出来了。

### 五、还没做的

- **没有真正的任务队列。** 后台任务是进程内的 `asyncio.Task`：进程重启就没了。`mark_stale_runs` 只能把它标成失败，**不会自动重跑**。要真队列得引入 worker 进程 + 持久化队列。
- **`wait=false` 是我改的新默认值**，动了原来的同步契约。理由：一个 3 分钟的 HTTP 请求在 web API 里就是 bug（代理和浏览器会先超时）。要同步显式传 `wait=true`。
- **并发上限 3 是拍的**，不是量出来的；"拒绝而不是排队"也是我的选择。
- **没有进度百分比**，只有 rounds / tool_calls 递增。
- **`search_prospects` 的真实网络路径我没有跑过** —— 只测过 patch 掉 DDGS 的版本，以及 `ddgs` 能 import。

**依据**：`app/agent/trade_tools.py`、`app/agent/service.py`、`app/agent/loop.py`、`app/agent/repository.py`、`app/routers/agent_runs.py`、`app/main.py`、`app/database.py`；"2950 ms vs 12 ms"和"13 ms"是**探针实测**（跑完已删，同样的性质由 `tests/test_background_runs.py` 覆盖）；依赖缺失是 `pip list` 与 `requirements.txt` 对照 + 实跑 `inspect_website` 得到；**571 个测试通过**（原 550）。

**置信度**：
- 阻塞工具冻住事件循环 —— **实测**（两种写法对比）
- 真实工具已不再阻塞 —— **实测**（patch 掉网络后的慢速 fetch）
- `requests`/`ddgs` 未安装、两个函数未定义 —— **实测**（实跑报错）
- 后台执行、开工前写行、进度写入、失败落地、429 上限、drain、stale 清扫 —— **实测**（11 个测试）
- 端到端抓取真实网页成功 —— **实测**（example.com）

**未验证部分**：
- **"3 分钟"这个量级我没有真跑过。** 我用的是 1 秒 × 3 页的探针，以及 1 秒的假 execute。真实模型 + 真实抓取的 3 分钟运行我没跑过。
- **并发上限和 SQLite 的 30 秒 busy timeout 都没在真实并发下压过。** 我只是把超时从 5 秒放宽，没有量出"database is locked"在负载下的出现率。
- **安装 `requests` / `ddgs` 是我替你做的决定**（它们本来就写在 `requirements.txt` 里，属于恢复声明状态）。如果你的环境有意不装，告诉我，我把 `test_the_declared_network_dependencies_are_importable` 改成 skip 而不是失败。
- **没有测过进程被强杀时的行为**：`mark_stale_runs` 的逻辑有单元测试，但"真的 kill 掉一个正在跑的进程再看下次启动"我没做。

## Q9. 确定性代码和 LLM 的边界在哪？你怎么保证它不被侵蚀？

**答案**：

边界是一条规则，不是一句口号：

> **确定性代码负责"存在什么、允许什么、已知什么"** —— 表结构、参数校验、预算、转录不变量、排期算术、**有名字的阈值**、写权限边界。
> **模型负责"什么重要、下一步做什么、怎么说"** —— 排序、打分、分类、措辞、要不要委派、什么时候停。
>
> 由此一条硬规则：**任何会被人拿去行动的分数或标签，只能来自两处 —— 模型（连同它用的证据），或者一个有名字、找得到、能被质疑的阈值。绝不能是分支里一个裸常量。**

### 一、规则必须能被执行，而不是被记住

侵蚀从来不长得像侵蚀，它长得像**"一个合理的默认值"**。我用 AST 扫了一遍 `app/`（判定字段 + 裸常量），找到三处真实的伪造：

| 位置 | 原来 | 问题 |
|---|---|---|
| `_basic_inquiry_analysis` | `customer_intent_score: 50` | 从一句 "hello" 到带交期的正式订单，**每个询盘都得 50 分** |
| `analyze_customer_website` | 抓取失败 → `score: 0` | 打不开的页面不是"零分线索"，而 0 会排到列表最底 |
| `_basic_reply_analysis` | `urgency: "medium"` | 不是从文本推的，也不是从任何东西推的 —— 就是个常量 |

三个都是同一个形状：**字段被人当作评估来读，而值是常量。**

### 二、修法

- `customer_intent_score` → `None`，理由写明"not assessed：没有模型，关键词规则产不出分数"。
- 抓取失败 → `score: None`。"没评估"不是"0 分"。
- `urgency` / `customer_mood` → `"not_assessed"`；新增 `judgement_source: "keyword_rules"`。
- **前端也修了同一个谎**：`inquiryResult.customer_intent_score || 0` 会把 `None` 渲染成一个 **0% 的仪表盘**。后端刚停止伪造，UI 立刻接着伪造。现在没有数字就不渲染仪表盘，显示 "n/a" + 原因（`lead_score` 同样处理）。

### 三、保证它不被侵蚀：把规则变成可执行的东西

新增 `tests/test_judgement_boundary.py`：

1. **扫描**：`app/` 下任何 dict 字面量，键名属于判定词汇（score / risk_level / priority / intent / sentiment / urgency / recommendation / verdict …），值是**裸常量** → 测试失败。
   - 唯一允许的常量是"未评估"词表：`None` / `""` / `"unknown"` / `"not_assessed"` / `"not_analyzed"` / `"not_mentioned"`。
   - 要豁免必须在**现场**写明理由：`# judgement-boundary: contract`。目前只有一处 —— `classify_prospect` 的 `required_output`，那是**向模型索要答案的格式**，正好是这条规则的反面。
   - **阈值模块不需要豁免**：`follow_up_policy.py` / `follow_up_plan.py` 用的是 dataclass 字段和命名常量，扫描本来就不命中 —— 我去掉豁免验证过，仍然 0 命中。
2. **守卫本身要被证明会红**：一个用例断言检测器认得 `customer_intent_score: 50`；我也手工把伪造塞回去验证过 —— 两个测试变红，恢复后全绿。
3. **边界的两半都断言**：`classify_prospect` 不得自己产出 score（只能列进 `required_output`）；`get_customer_signals` 不得返回 `risk_level`/`priority`。
4. **反向也要守**：排期必须是算术。`test_the_schedule_is_arithmetic_and_not_a_model_call` 断言 `follow_up_plan.py` 里不出现 `complete_text` / `get_client` / `llm` —— 因为"这个客户为什么排在周二"必须可复现、可解释，模型给不了这个保证。

### 四、边界现在画在哪

| 归确定性代码 | 归模型 |
|---|---|
| 表结构、字段校验、JSON schema | 哪个客户重要 |
| 预算（轮次 / 调用 / token / 墙钟 / deadline） | 下一步做什么 |
| 转录不变量（配对、截断整批拒绝） | 用哪个工具 |
| 排期算术（退避、每日上限、quit rule） | 措辞、角度、语气 |
| 阈值（有名字、有边界测试、可改） | 要不要委派 |
| 写权限（注册表里没有 send / delete） | 什么时候停（给出最终答案） |
| 派生事实（thread state、统计、trace） | 证据够不够 |

### 五、还没做的 —— 这一节是这份答案里最该看的

- **关键词规则仍然是"用确定性代码回答判断问题"，只是现在被标出来了。** `analyze_email_reply` 的 intent / sentiment、`analyze_inquiry` 的 inquiry_type / urgency 都是子串匹配。它们被 `test_characterize_classifiers.py` **当作已知错误钉住**（包括 "no rush 被判 high" 那个 bug），钉住的理由就是等工具调用替换它们。
  **扫描抓不到它们** —— 因为它们的值是变量，不是常量。这是一个真实的守卫盲区，我在测试注释里写明了，没有假装它不存在。
- **`_RECOMMENDATION_TO_PRIORITY`**（`scan_runner`）把模型的 `approach_now` 映射成 `high`。这是"翻译模型判断"，不是"替模型判断"，我把它算合法 —— 但它确实有损，而且没有测试说明为什么这五个词对应这三个桶。
- **没有 CI。** 所有守卫都靠人跑 `pytest`。我没有配 pre-commit 或 CI，所以"不被侵蚀"目前的实际保证是"下一个跑测试的人会看见"。

**依据**：`app/services/agent_service.py`、`app/agent/trade_tools.py`、`app/services/follow_up_plan.py`、`frontend/src/views/Agent.vue`；三处伪造是 AST 扫描找到的；扫描、豁免、守卫失效验证都是实测；**580 个测试通过**（原 571），前端 build 通过。

**置信度**：
- 三处伪造与修法 —— **实测**（扫描 + 单元测试 + 手工塞回去验证守卫会红）
- 前端把 None 渲染成 0% —— **从代码读出**（`|| 0`），我没有在浏览器里看过渲染结果
- 阈值模块不需要豁免 —— **实测**（去掉豁免后扫描仍 0 命中）
- 边界的两半都断言了 —— **实测**

**未验证部分**：
- **我没有在浏览器里点过**这些改动后的页面。前端只验证到 `npm run build` 通过。
- **判定词汇表是我定的**，不是穷举来的。`stage`、`tier`、`bucket` 这类新词如果出现，扫描不会命中 —— 守卫只覆盖它认识的词。
- **关键词规则的实际错误率我没有数据。** 我只知道 "no rush" 那一类被钉住的例子。
- **没有真实的多轮使用。** "侵蚀"是随时间发生的，而我只有一次扫描的快照；下次有人加一个"合理的默认值"时，这条规则能不能拦住它，取决于它写不写在这些词上。

## R10. 客户同一封邮件被处理两次会怎样？幂等在哪一层？

**答案**：

幂等在**三层**，按"谁真正保证它"排序：

1. **行状态就是锁。** `pending → sending` 是一条原子的
   `UPDATE ... WHERE status = pending`。两个 worker —— 两个请求、两个进程、
   或者崩溃后的重试 —— 不可能都拿到它，因为第二个看到的是"没有可更新的行"。
   **正确性靠这一层。**
2. **`tracking_id` 就是幂等键。** 它是 `UNIQUE` 的。调用方给同一个
   `Idempotency-Key`，第二个请求就拿到同一行；那一行已经发出去的话，返回原始
   结果而不是再发一封。**实测**：把应用层的重放检查关掉，第二次插入直接撞
   `UNIQUE constraint failed: email_logs.tracking_id` —— 数据库自己拒绝。
3. **进程内锁**（`_SEND_LOCK`）只是一句礼貌：明显并发的第二次发送在动手之前
   就拿到一个能读懂的 409。它跨不了进程，也活不过崩溃。

**不宣称 exactly-once。** 进程如果在 SMTP 交出去之后、写状态之前死掉，那封邮件
到底发出去没有，这里无从得知。这种行留在 `sending`，由启动时的
`mark_stale_sends` 判成 `failed` 并在错误信息里写明"outcome unknown"。猜的话
只能二选一：要么给客户发两封，要么悄悄丢一封。

### 一、查出三处"处理两次就出事"，都是真的

| 位置 | 原来会怎样 |
|---|---|
| `create_email_draft`（agent 的写工具） | **零去重**。重试、连点、同一天跑两次同一个目标 → 两张一模一样的待审草稿。**两张不是一个活干两遍，是一个活列了两行**；人顺着列表点下去，客户收到两封 |
| `POST /emails/send`（手动发送） | 先发信、后写记录，**没有任何幂等键**。客户端重试或双击 → 两封真邮件，两个不同的 tracking_id |
| `POST /emails/send-pending`（批量） | 循环里发完所有草稿，**最后才 commit 一次**。中途崩溃 → 已经发出去的十封状态全部丢失，下次运行再发十封。**十个客户，二十封邮件** |

第三处是最大的一处，而且只有读代码才能看出来：批量循环里每一行只有在循环结束后
才落盘。

### 二、修法

- **`create_email_draft` 拒绝重复**：同一客户 + 同一主题（大小写、首尾空格无关）
  且**仍在等待审核**的草稿已存在 → 返回 `status: "duplicate"` + 已有草稿 id，
  不新建。不同主题仍然允许（回复询价和催单是两封不同的邮件，只有人知道是哪种）；
  第一封已发出或已被否决后，同主题的新草稿也允许 —— 那正是该跟进的时候。
- **`POST /emails/send` 支持 `Idempotency-Key`**：键决定 `tracking_id`
  （`idem-<sha256 前 24 位>`），所以重放可辨认。行为分三种：已发出 → 返回原记录
  （`replayed: true, already_sent: true`）；**在飞** → 409，不猜；上次失败 → 409，
  让调用方决定（失败的那次可能其实到了）。
- **行在邮件交出去之前就写**（状态 `sending`）。顺序就是崩溃保护：先发后记，
  中间崩溃不留痕迹，下次就再发一遍。
- **批量改成逐行 claim + 逐行 commit**：崩溃最多损失正在发的那一封，而它的结果由
  `mark_stale_sends` 如实报成"未知"。
- `EmailStatus` 增加 `SENDING`。**不需要迁移**：SQLite 里是普通 VARCHAR、没有 CHECK
  约束，SQLAlchemy 存的是枚举**名字** —— 这一点用原始 SQL 断言过（ORM 读回来是枚举
  对象，问 ORM 等于问 ORM 而不是问数据库）。
- 启动时清扫遗留 claim。

### 三、一个自己踩到的坑（记下来，因为它正是本题的反面）

我第一版的新测试用了 demo 客户 4，并且在它身上留下了 7 张待审草稿 ——
**另一个文件的测试随后就红了**（客户 4 的跟进理由从"还没回音"变成了
"7 份草稿等你审批"）。

改完之后又红了一次，原因更微妙：我新建的 18 个测试客户是 `contacted` 阶段，
**会被排进跟进计划**，而计划有 `max_actions_per_day=20` 的日上限 —— 客户 4
被挤出了当天的清单，`follow_up_action()` 返回 `None`。

修法是让这些客户 `stage="completed"`（关闭阶段，计划根本不看），并在测试里写明
理由。**测试数据的隔离本身就是幂等/边界问题的一部分**：不然你测的是别人的状态。
（顺带确认：计划确实把超出的条目计数在 `deferred` 里，不是静默截断。）

## R11. 状态存哪？3 个月后那个客户回来了怎么办？

**答案**：

### 一、状态在哪：一个数据库，一列承诺，其余全是算出来的

| 存哪 | 什么 | 为什么 |
|---|---|---|
| 一个 SQLite 文件 | 全部业务状态：`customers` / `customer_contacts` / `email_logs` / `email_templates` / `tasks` / `agent_runs` | 单进程单写者（`start.bat` 不带 `--workers`），所以不需要分布式协调 |
| `email_logs` | 每封邮件的事实：`status`、`sent_at`、`replied_at`、`tracking_id`(UNIQUE)、`error_message` | 时间戳是事实，枚举是记账 |
| `customers.next_follow_up_at` | **唯一的计划承诺列** | 让下一次运行是增量的，而不是每轮把同一批客户重新决定一遍 |
| **不存** | `ThreadState`（`awaiting_reply` / `they_wrote_last` / `reply_owed_days` / `pending_proposals` …） | **每次从 `email_logs` 纯函数推导**。存一份就是第二份真相：记录回复时忘了改标志位，两份立刻不一致 |
| **不是状态** | `_SEND_LOCK`、APScheduler 的 job store、agent 的 spill 文件 | 锁是礼貌不是保证；定时任务启动时从代码重新注册，重启不丢东西 |

一句话：**能推导出来的，不存。**（结构上排除了"标志位和事实漂移"这一整类 bug。）

### 二、3 个月后：两种完全不同的情况

**情况 A：他们写了。** `replied_at` 是新的 → `they_wrote_last` → 普通的"该你回了"。
**但这要求记录的是"他们什么时候写的"，不是"我们什么时候看见的"。**

这里有个真问题：`/logs/{id}/reply` **一直支持** `replied_at`（还校验了不能是未来、
不能早于发信时间），**但前端从来不传** —— `recordReply(row.id)`，于是三个月的旧消息
被记成"刚刚"，`reply_owed_days = 0`，计划把它当新的回信，churn 风险也全错。
**能力存在，产品没用。**（和邮件模板里的 `[AI 不可用` 分支、早报的
`generateFallbackBrief` 是同一类问题：降级/能力写好了，没人接上去。）

已修：`markReplied` 现在问一句"是刚刚收到的吗？"，选"他们早就写了"就填日期；
默认仍是"刚刚"（常见情况一次点击）。**实测**：同一封三个月前的邮件，记成"今天"
→ `answer_them`；如实记成 90 天前 → `review`。两条路径都有测试。

**情况 B：我们三个月没回。** 这是修之前更糟的一半：计划**永远**给
`answer_them` + 高优先级，和今天早上刚到的那封回信**完全一样**，只有 reason 里
那个数字不同。于是应用会一直建议"回复他们的消息"—— 把一封例行跟进发进一个
季度前就结束的对话，还排在列表最前面。

已修：新增 `reply_too_late_after_days = 30`。超过它的回信，动作类型从
`answer_them` 变成 `review`。**实测（走真实查询路径，不是单元断言）：**

```
90 天没人回：kind=review   priority=high
  reason   : They wrote 90 day(s) ago and nobody answered - too late for a routine reply
  suggested: Decide: restart the conversation with an apology, or close this customer
  draft    : no
今天刚回：  kind=answer_them priority=high
  reason   : They replied 0 day(s) ago and have not heard back
```

`review` 不在 `EMAILING_KINDS` 里，所以**不会自动生成道歉信** —— 道歉不是一个
可以自动生成的东西。优先级保持 high：这是一次没兑现的承诺，不该沉到新的陌生开发
下面。顺序也仍然正确：队列里已有待审草稿时，那条规则（第 0 条）优先 ——
**那张草稿很可能就是对他这封信的回复。**

### 三、R10 的补记（上一轮只写在"未验证"里，没做）

前端现在每次发送都带幂等键：

```js
send: (data, options = {}) => api.post('/emails/send', data, {
  headers: { 'Idempotency-Key': options.idempotencyKey || sendKey(data) },
})
```

键不是随机的 —— 随机键每次都是"新请求"，等于没防。键由**发送内容 + 当前分钟**
推导（FNV-1a），所以同一分钟内的两次相同发送是**同一次逻辑发送**，第二次拿回第一次
的记录（`replayed: true`）而不是第二封邮件；换内容或过一分钟就是新的发送。

**实测**：同内容同分钟 → 同键；同内容下一分钟 → 不同键；改正文/收件人/主题 →
不同键。UI 收到 `replayed` 时不再说"发送成功"，而是说"刚才已经发过了，没有重复发送"。

### 四、还没解决的真实缺口

**没有收件箱。** 应用不会知道客户来信，除非有人手动记录 —— 而且**只能记在"我们发过的
某封邮件"上**（`/reply` 要求 `email_id`，且拒绝从未送达的邮件）。所以"客户主动回来，
写一封全新的信"这种情况，**在当前数据模型里无法如实记录**：没有 direction 列，
而给现有库加列做不到（`create_all` 只建表）。人只能加备注。
**这是缺口，我没有解决它，只是把它说清楚。**

**依据**：`app/services/follow_up_plan.py`、`app/services/follow_up_policy.py`、
`app/routers/emails.py`、`frontend/src/api/index.js`、`frontend/src/views/Emails.vue`；
**11 个新测试**（`tests/test_state_and_the_returning_customer.py`）；端到端行为用一个
临时探针跑过真实数据库（跑完已删）；幂等键语义用 node 直接跑 ESM 模块验证；
**609 个测试通过**（原 598），前端 build 通过。

**置信度**：
- 状态清单、"能推导就不存" —— **从代码读出**
- 前端不传 `replied_at` → 三个月旧消息被当成新的 —— **从代码读出**，且用推导函数实测了两条路径
- 30 天阈值让动作变成 `review`、不出草稿、优先级 high —— **实测**（单元 + 端到端探针）
- 幂等键语义 —— **实测**（node 直接跑）
- 守卫会红 —— **实测**（关掉 `too_late` 分支，3 个测试变红）

**未验证部分**：
- **30 天这个阈值是拍的**，不是量出来的。选它的理由是同行业报价的"过期"感觉，
  不是数据。
- **前端日期输入没法自动测**（这个仓库前端没有测试框架），只有 `npm run build`
  通过和手工语义检查。
- **`review` 在 UI 上只是个标签**，没有"关闭客户"的闭环流程 —— 建议里写了
  "或者关闭这个客户"，但产品里没有一个动作能真正完成它。
- **没有备份、没有迁移路径**：那个 SQLite 文件是唯一副本，`create_all` 只建表不加列。
  真要上生产，这是第一件要解决的事，而我没动它。

## R12. 怎么 debug 一次失败的客户处理？

**答案**：

### 一、debug 从哪一头开始

人问的是"Martin 这周为什么什么都没收到"，起点是**客户**。而这个旅程原来走不通 ——
事实散在四个互不引用的地方：

| 事实在哪 | 为什么走不通 |
|---|---|
| `email_logs` | 有邮件和失败原因，但看不到计划是怎么想的 |
| 跟进计划 | 能给整本书的决策，但**看它要 POST，而 POST 会写 `next_follow_up_at`** —— 观察会改变被观察的东西 |
| `agent_runs` | 有轨迹，但**完全没有客户字段**：只有一段自由文本 goal 和一个 JSON trace，所以无法从客户找到"处理过他的那次运行" |
| `ThreadState` | 每个规则真正读的那组数字，从来不显示给人看 |

### 二、加了什么

`GET /api/v1/customers/{id}/debug` —— 一次请求回答"这个客户发生了什么、为什么"。
**只读**（计划用 `persist=False` 构建，所有查询都是 SELECT）。

返回：客户记录 + 联系人 + **推导出的 ThreadState**（规则读的就是这组数字）+ 邮件列表
（含 `error_message` / `tracking_id` / 各时间戳）+ **计划的决策及其 `evidence`** +
接触过他的 agent 运行 + 备注 + churn 评估。

最有用的部分是 `findings`：同样的事实，按"最可能的原因在前"用大白话说一遍。
**实测**（一次真实的失败处理，探针跑完已删）：

```
findings:
  - The most recent failed attempt is email 1 (failed):
    SMTPAuthenticationError: 535 authentication failed
  - 1 draft(s) are waiting for a human decision (oldest 1 day(s)).
    Nothing further is proposed until that decision is made.
  - The plan's next action is 'awaiting_approval' (medium), due ...
  - No agent run has ever mentioned this customer. If an analysis was
    expected, it did not reach them.

plan.evidence: {..., 'pending_proposals': 1, 'pending_proposal_days': 1,
                'approval_reminder_after_days': 2}
```

`evidence` 是关键：**决策自带它用的数字**，所以"为什么是这个结论"可以核对，
而不是只能相信。

### 三、两个设计要点

1. **只读。** 用 POST 版计划去调查，会把你要调查的东西改掉，而且你没法看第二次。
2. **按参数匹配，不按子串。** 在运行的 trace 里找 `customer_id`，是解析 JSON 之后
   比参数 —— `"4"` 出现在 `"14"` 和 `"40"` 里面，**一个显示别人运行的 debug 视图
   比不显示更糟**。goal 文本匹配也算，但标了 `matched_by`，让人自己判断。

### 四、这一轮我又踩了同一个坑（第三次，所以记下来）

新测试留下 18 个 `contacted` 客户 → 计划的 `max_actions_per_day=20`（当天清单是
按到期时间排序的前 20 条）把 demo 客户挤出去 → **另外两个文件的测试红了**。

改成关闭阶段后又发现第二层：**SQLite 会把删除行的 id 直接给下一个插入**。我留下的
run 行（goal 里写着 `review customer N`）于是成了新客户 N 的"历史"，一个断言
"从来没有运行碰过这个客户"的测试因此失败。

最后的修法是让测试**自己清理**：fixture 结束时删掉自己创建的客户和运行。
**测试数据是共享且被限量的资源，不是免费的。**

顺带修了一个真 bug：`test_follow_up_plan.py` 的 `customer_row()` 用
`GET /customers/`（默认每页 20）翻页找客户，**它一直在假设整本书不超过 20 行**。
生产里书是会长的 —— 改成直接 `GET /customers/{id}`。

### 五、还没做的

- **trace 的搜索是扫描**：最多看最近 300 次运行，没有索引。答案里带了
  `runs_scan_truncated`，而不是假装完整。
- **没有前端页面。** 视图只有 API，人得用 curl 或文档页看。
- **`matched_by: "goal text"` 是启发式**：只有 goal 里写了客户名字或 id 才算；
  改名或 id 重用会误配（id 重用这一点我这轮实测到了）。
- **spill 文件没暴露**：长运行里被压缩掉的观察还躺在磁盘上，一次分析读过什么、
  裁掉了什么，仍然只能去文件系统看。

**依据**：`app/services/customer_debug.py`（新）、`app/routers/customers.py`、
`tests/test_customer_debug.py`（新，16 个测试）、`tests/test_api_contract.py`（路由表）、
`tests/test_follow_up_plan.py`（helper 修复）；只读性、参数匹配精度、截断标记、
"没有任何运行碰过"都是实测；**625 个测试通过**（原 609），连跑两遍一致。

**置信度**：
- 四处事实互不引用、POST 计划会写状态 —— **从代码读出**
- 视图只读（GET 两次后承诺与邮件数不变）、而 POST 确实会写 —— **实测**（两个对照测试）
- 参数匹配不会把 14 号当成 4 号 —— **实测**
- findings 的实际输出 —— **实测**（探针跑真实数据库）
- 截断标记 —— **实测**

**未验证部分**：
- **没有按时间线排序的视图。** 邮件和运行是两个列表，人得自己在脑子里对齐时间。
- **没有"这次处理为什么失败"的单点结论。** findings 是并列的几条，不是一棵
  因果树；如果失败原因不在这些规则覆盖的范围内（比如 provider 反复超时但最后成功），
  视图不会指出它。
- **运行扫描只覆盖最近 300 次**，更早的运行找不到，且只在 `runs_scan_truncated`
  为 true 时才提示。
- **没有权限控制**：这个视图包含客户邮箱、失败原因和完整备注，而 API 目前没有认证。

## R13. 队列积压 1000 条了怎么办？

**答案**：先量，再分清是哪条队列。实测（1000 客户 × 每人 3 封邮件）：

```
whole-book plan : 78-94 ms   actions=20  deferred=980  commitments=1000
debug 一个客户   : 125 ms
due-only plan   : 62 ms
```

**计划的算术没有问题** —— 这一点要先说清，因为它是最容易被怀疑的部分。1000 条积压的
真实问题在别处，一共三个：

### 一、一次请求想发完整个队列

`POST /emails/send-pending` 读**所有** pending 并全部发送。1000 条 = 一个请求里几分钟的
SMTP，**整个过程握着发送锁**（期间任何其它发送都是 409），客户端先超时，操作者不知道
发到哪了，而且**完全没有顺序**（数据库返回什么顺序就是什么顺序）。

这是"积压 1000 条"最直接的答案：**队列必须分批排空，而且要把进度说出来。**

- `limit`（默认 50，上限 500），按 `created_at` **最旧优先**，返回 `remaining`
  （本批之后还剩多少）。
- **可续**：每行在发送前先 claim 并 commit（R10 做的），所以中断后下一次接着发，
  不会重发，也不会漏。
- 前端循环分批（25/批），显示 `Sent 50 - 950 left`；中途失败会说清"已发多少、还剩多少"。
- **积压时不要提高每批上限**：那只会让一次请求更长、锁更久、更容易超时。

### 二、debug 一个客户要算整本书

R12 的调试视图是"算整本书、再挑出这一个"：**1000 客户时 125 ms / 次**，随书线性增长，
而且每次打开客户页都持有一次全库读事务。抽成 `plan_for_one_customer`（同一个推导函数，
只是列表里只有一个元素）之后：

| | 修前（1000 客户） | 修后（**3000** 客户） |
|---|---|---|
| debug 一个客户 | 125 ms | **15 ms** |
| 整本书计划 | 78-94 ms | 250-266 ms |

加了守卫测试：**单客户路径必须和整本书路径对同一个客户给出同样的
kind / priority / reason / due_at** —— 快的那个如果答案不一样，那就不是快路径，
是第二份实现。

### 三、积压是看不见的

`deferred: 980` 一直在 API 响应里，**UI 里一个地方都没有**。所以人看到"今天 20 条"，
不知道还有 980 条在等。调试视图现在带 `backlog`：`customers_in_play` /
`pending_drafts` / `max_actions_per_day` / `days_to_clear_if_all_waiting`。

这个数字**从策略里读，不复制**（有测试断言它是读的）。1000 条 ÷ 20/天 = **50 天**；
3000 条 = **149 天**。R12 里的 `plan_deferred_past_cap` 换成了 `backlog` ——
前者需要算整本书，正好是上面第二个问题。

### 四、真的要处理 1000 条，顺序是

1. 先看 `deferred` 和 `backlog`，分清是"计划在排队"还是"草稿等人审"。
2. 计划排队 → `max_actions_per_day` 是唯一的闸门；20/天要 50 天。
3. 草稿积压 → 分批发，盯着 `remaining` 降到 0。
4. 两者都不是 → 那 1000 条不在这两条队列里（比如 run 队列：并发上限 3，超过直接 429，
   它**没有队列**，这是设计）。

### 五、这一轮自己踩的坑

用 PowerShell 往两个前端文件里插行时写进了裸 LF，**同一个文件里 CRLF/LF 混用** ——
被本会话早先加的 `test_no_file_has_mixed_line_endings` 抓住了。已统一成 CRLF。
（这是同一个人第二次栽在行尾上；守卫是值得的。）

**依据**：`app/routers/emails.py`、`app/services/agent_service.py`、
`app/services/customer_debug.py`、`frontend/src/views/Emails.vue`、
`frontend/src/api/index.js`；**11 个新测试**（`tests/test_backlog.py`）；
1000/3000 客户的耗时是**探针实测**（跑完已删）；守卫验证过"关掉就红"
（去掉 limit 或改掉排序，3 个测试变红）；**635 个测试通过**（原 625），连跑两遍一致；
前端 build 通过。

**置信度**：
- 三个问题都是**从代码读出**，耗时是**实测**
- 分批上限、最旧优先、`remaining`、重复调用能排空 —— **实测**
- 单客户路径与整本书路径一致 —— **实测**（不一致就红）
- `backlog` 从策略读数、草稿计数 —— **实测**
- debug 15 ms @3000 vs 125 ms @1000 —— **实测**（不同规模，不是同规模对照）

**未验证部分**：
- **`max_actions_per_day=20` 依然是拍的**。"1000 条要 50 天"是算出来的（1000 ÷ 20），
  不是压测出来的。
- **整本书计划仍是 O(书)**：3000 客户 250-266 ms，线性。日上限只裁剪**输出**，
  不减少计算 —— 因为每个客户的承诺都要写。10k 客户大约 1 秒/次，而每次运行、每次
  手动看计划都要付这个成本。我没做增量或分页。
- **没有队列位置反馈**：客户只能知道"今天没轮到你"，不知道"排在第 812 位"。
- **没有并发 worker、没有速率控制、没有退避**：排空靠调用方串行循环；SMTP 限流
  会表现为一条条失败，而不是被限速。
- **`deferred` 只是个计数**：被挤掉的是哪些客户，API 不说。想查具体某人，得用 R12
  的调试视图单独看。
- **前端分批循环没有自动测试**（前端没有测试框架），只有 `npm run build` 通过。
- **没有在 1000 条真实草稿上跑过发送**：分批逻辑测的是 5 条，SMTP 是 stub 的。

## R14. 如果让你重写一次，你会改哪个决定？

**答案**：

### 一、改这一个：`create_all()` 之后没有迁移路径

原来建库只有一句 `Base.metadata.create_all`：表不存在就建，**已存在的库永远不再碰**。
第一天没问题，从第二天起全错。这一个决定塑造了这个代码库里相当多的东西 ——
下面每一条都是它的**绕道**，不是坏代码，是对一个本不该存在的约束的合理回答：

| 绕道 | 为什么不得不这么写 |
|---|---|
| 幂等键塞进 `tracking_id` | 没有列可以放调用方的 key（`tracking_id` 恰好 UNIQUE） |
| `EmailStatus.SENDING` 靠"加枚举成员安全" | 加**列**无处可加；加成员只是因为 SQLite 存的是 VARCHAR 且没有 CHECK |
| `agent_runs` 靠**扫 JSON trace** 找客户 | 没有 `customer_id` 列，无法索引 |
| "客户主动回来写一封全新的信"**表达不了** | 没有 `direction` 列，也没法加 |

R11 我当时写的是"真要上生产，这是第一件要解决的事，而我没动它"。这一轮就动它。

### 二、修法：一个刻意做小的迁移器

`app/migrations.py`：

- **一张表** `schema_migrations` 记录已应用的和时间。不是框架；**没有 down** ——
  生产里回滚 schema 是人拿着备份做的决定，不是一次方法调用。
- **每个迁移自带 guard**（`already_applied`），不只信版本表。因为**新库从
  `create_all` 就拿到了最新 schema**，列已经在了；只信版本表的话，每次全新安装
  都会去加一个已存在的列然后崩。**实测**：把 guard 去掉，`duplicate column name:
  customer_id`。
- **按顺序、每个迁移一个事务**，失败即停 —— 半应用比不应用更糟，因为它看不见。
- **会报告做了什么**，启动时打日志（`applied / already_present / pending`）。
  迁移悄悄跑完而没人知道，是 schema 和人以为的样子开始分叉的方式。

### 三、第一个真迁移：`0001_agent_runs_customer_id`

正好用来消掉上表里第三条绕道。

- `agent_runs.customer_id` + 索引（迁移里 `ALTER TABLE ... ADD COLUMN` + `CREATE INDEX`）。
- `POST /agent/run` 可以带 `customer_id`；**不存在的客户会被 404 拒绝** ——
  SQLite 默认不强制外键，写进去只会静默匹配不到任何东西，那比拒绝更糟。
- 调试视图**优先走列**（一次索引查询），**只对 `customer_id IS NULL` 的老行**才扫
  trace。两条路径都有测试，所以哪条都不会被当成死代码删掉。

**实测（真的在用的开发库 `tradeagent.db` 上跑的，跑前备份）：**

```
before: agent_runs 没有 customer_id
run init_db()          # 应用启动时做的同一件事
after : columns = [..., 'customer_id']
        indexes = ['ix_agent_runs_customer_id', 'ix_agent_runs_run_id']
        schema_migrations = ['0001_agent_runs_customer_id']
        agent_runs 原有 2 行 → 仍然 2 行
```

**测试覆盖的是"已经在用的库"**（这才是迁移的意义）：旧结构建库 → 迁移 → 列出现、
索引出现、旧行还在且 `customer_id` 为 NULL（**不去编一个客户给它**）；迁移两次
不重复执行；新库记录为 `already_present` 而不执行；坏迁移后面的迁移不跑。

### 四、如果还能再改一次

1. **`email_logs.direction`** —— 让"客户主动来信"能被如实记录。这正是 R11 里我
   说不出办法的那个缺口，现在唯一的阻碍没了。
2. **有类型的 UTC 时间**（现在全是裸 `datetime.utcnow()`）：跨时区会咬人，
   而这是个中国团队跟德国买家做生意的应用。
3. **`run_status` 不该是自由文本**：`running/succeeded/...` 散在代码里，
   枚举成员在 R10 已经证明是安全可加的。

**依据**：`app/migrations.py`（新）、`app/database.py`、`app/models/agent_run.py`、
`app/agent/{loop,repository,service}.py`、`app/routers/agent_runs.py`、
`app/services/customer_debug.py`、`tests/test_migrations.py`（新，10 个测试）；
真实开发库上的迁移是**实测**（跑前备份，跑后逐项核对）；**647 个测试通过**（原 635），
连跑两遍一致。

**置信度**：
- "这一个决定造成了那些绕道" —— **从代码读出**（每条都有出处）
- 旧库能迁移、旧行不丢、重复迁移无副作用、新库不误执行、坏迁移即停、guard 必要 —— **实测**
- 真实开发库迁移成功且行数不变 —— **实测**
- 列优先、老行仍可扫到 —— **实测**（两条路径各一个测试）

**未验证部分**：
- **没有回滚。** 只有前进。回滚靠备份（`.gitignore` 里已加 `*.backup-*`），
  这是有意的，但意味着"迁移写错了"的代价是恢复备份。
- **只在 SQLite 上验过。** SQL 是 SQLite 方言（`PRAGMA table_info`、`ALTER TABLE
  ADD COLUMN`）；换 Postgres 要改 guard 的实现。
- **没有并发保护。** 两个进程同时启动并同时跑迁移，可能都尝试应用同一个 ——
  单进程部署下不会遇到，多 worker 会。
- **数据迁移（回填）还没写过。** 这个迁移只是加列；回填 `customer_id` 需要解析
  历史 trace，我没做，所以**老行的客户关联仍然是靠扫描**（有明确标注）。
- **真机迁移之后没有跑过完整的应用启动流程**（我用的是 `init_db()` +
  直接读库），也没有在浏览器里点过。

## R15. FastAPI 是 async 的，所以你的服务就是异步的？

**答案**：**不是。** 而且比"不是"更具体：**在这里，并发会让事情变慢。**

FastAPI 是 async，只说明**框架**能在请求 await 的时候去跑别的任务，完全不说明这个请求
*做了什么*。两种"看起来异步、实际不是"的情况，这个代码库里都有。

### 一、协程里的阻塞调用（有，已修）

写了个 AST 审计：遍历所有 `async def` 的函数体，找会停住事件循环的调用
（`requests.*` / `open()` / `time.sleep` / `smtplib` / `subprocess` …），
**跳过嵌套的同步 `def`** —— 因为"嵌套同步函数 + `to_thread`"正是修法本身，不是问题。

结果：**只剩两处**，都是 `open()` 读扫描结果 JSON（导入线索和预览线索两个路由）。
已改成 `asyncio.to_thread(_read_leads_file, path)`。

（Q8 已经修过 `inspect_website` / `search_prospects` / `analyze_customer_website`；
`aiosmtplib` 本来就是真异步。）

### 二、"不是调用的同步工作"（审计看不见，人也看不见）—— 实测

3000 客户 × 每人 3 封邮件：

```
SELECT customers                              0.016s
load emails/contacts + derive threads         0.203s   （await 的 I/O + ORM）
plan_follow_ups（纯 Python，会占住循环）        0.015s
```

**这纠正了我自己在 R13 的说法**：我说整本书计划是"O(书) 的计算"，暗示它占 CPU。
实际它 0.2 秒里绝大部分是 **await 的数据库往返**，纯 Python 只有 15 毫秒。
审计看不到这一层，但量一下就知道。

### 三、真正让人意外的那个数：并发更慢

```
1 次计划运行                  0.282s
4 次计划并发                  1.984s     （顺序做大约 1.0s → 并发是它的 2 倍慢）
50 次平凡读取 顺序             0.031s
50 次平凡读取 并发             0.063s     （也是 2 倍慢）
```

**"异步"卖的是并发，这里并发是负收益。** 我把 SQLite 的常规答案也试了：
`journal_mode=WAL` 只改了 3%（2.05s → 1.98s），所以**日志模式不是主因**。
剩下的候选是：每连接的固定开销、行→ORM 对象这一步只能在单线程里做、以及只有一个写者。
**哪一个占主导我没有分离出来**，这个文件也不假装知道。

（WAL 我留下了：它没修好这个测量，但没有它，一个写事务会挡住所有读者，而这个应用会在
服务请求的同时写进度。设置本身有测试钉住 —— 包括它实际返回 `wal`。）

### 四、落成永久守卫

`tests/test_async_honesty.py`：

1. **审计变成测试**：`app/` 下任何 `async def` 里出现阻塞调用就红。豁免要写进
   `ALLOWED`（目前是空的）—— 加进去应该感觉像做决定，因为它就是。
2. **审计自己也要被证明会红**：两条用例分别断言"认得 `requests.get`"和
   "嵌套同步函数 + `to_thread` 不算"。
3. **pragma 有测试**：WAL 和 `synchronous=NORMAL` 是能被静默删掉的设置，
   所以从真实连接上读出来断言。

我手工把 `time.sleep` 和 `open()` 塞回一个协程，守卫如期报出两条并定位到行号。

### 未验证部分

- **没有真实的压测**：上面是单进程直调服务层，不是 HTTP 并发；uvicorn 的
  连接处理、代理、keep-alive 都没进来。
- **并发变慢的根因没有分离**（见上）。
- **没有试过 `--workers`**：多进程能绕过一部分问题（每个进程一个事件循环、
  一个 SQLite 连接），但会带来多写者与连接池的新问题，我没测。
- **没有测过 `aiosqlite` 的线程池上限**：阻塞工具（网页抓取）走的是
  `asyncio.to_thread` 的默认线程池（`min(32, cpu+4)`），并发抓 30 个页面会排队 ——
  这一条我只是推的，没测。
- **LIMIT/流式**：计划接口会把整本书读进内存，我没有做分页或流式，也没有测大书下的内存曲线。

**依据**：`app/routers/agent.py`、`app/database.py`、`tests/test_async_honesty.py`（新）；
所有耗时都是**探针实测**（3000 客户，跑完已删）；守卫失效验证是**实测**；
**651 个测试通过**（原 647），连跑两遍一致。

## R16. 为什么用 AsyncOpenAI，不自己用 httpx 包一层？

**答案**：**因为手写 httpx 要自己重做的，恰好是这份工作里真正难的那部分。**

SDK 已经做好了这些，而且做得比我写得好：

- **把一次失败请求分类**：超时 / 连接错误 / 限流 / 认证被拒 / 5xx，是五件不同的事；
- **该重试的用退避重试**（默认 2 次，覆盖连接错误、408/409/429/5xx）；
- **连接池**（Q2 之前有 10 处各自 `AsyncOpenAI(...)`，每次调用新建连接池，这就是当时的实况）；
- **响应结构**（`choices[0].finish_reason`、`usage`、tool_calls）；
- **换 provider**：`base_url` 一个参数就够（MiMo / DeepSeek / OpenAI）。

自己包一层 httpx 意味着**拥有上面全部逻辑**，还得从 HTTP 状态码重新推导这套分类 ——
而且出问题的时候，那是我们自己的 bug，不是库的。

**但 SDK 不会用这个代码库的语言说话。** 这才是要修的地方。

### 一、接缝在漏（真实缺陷）

`app/llm.py` 的 docstring 写着"异常是重点，不是实现细节"，定义了三种状态：
没有 key / 被截断 / 返回不可用。但它**没有把 provider 自己的异常翻译过来** ——
于是超时、限流、密钥被拒这些全部以 `openai.APITimeoutError` 之类的身份漏出去。
调用方只能这么写（`ai_service.py` 的原话，注释就是缺陷本身）：

```python
except Exception as exc:                      # network, auth, rate limit
    reason = f"model call failed: {exc}"
```

**四种不同的情况压成同一个字符串。** 而这个服务整套降级叙事（R9）讲的就是"要说清
*为什么*降级"。

### 二、修法

1. **补全分类**：`LLMRateLimited`（限流，过一会儿可以再试）、`LLMTransient`
   （超时/连接/5xx，SDK 已经重试过 `DEFAULT_MAX_RETRIES` 次）、
   `LLMUnavailable`（没配 key **或** key 被拒 —— 都需要人去改），
   加上原有的 `LLMTruncated` / `LLMBadResponse`。
2. **`translate_provider_error()`**：按异常的**模块名 + HTTP status** 判断，
   不 import SDK 的具体异常类 —— 那些类会在版本之间改名重组，一个因为枚举了库的
   内部结构而崩掉的接缝不叫接缝。
   **关键性质：不是 provider 的异常就原样抛回去。** 我们自己的 `TypeError`
   绝不能被上报成"模型调用失败" —— 那是一个真 bug 藏在友好降级后面的标准方式。
   有测试专门钉这一条。
3. **重试次数写死出来**：SDK 默认 2 次，之前是**隐式继承的默认值** ——
   "会重试几次、中间干什么"是个决定，未声明的默认值会在升级时悄悄变。
   现在 `DEFAULT_MAX_RETRIES = 2` 显式传给客户端，并进缓存签名。
4. **第二个接缝也统一**：`app/agent/protocol.py`（agent 运行时自己的适配器，
   需要 tool calling，所以不走 `app/llm.py` 的调用）用**同一个翻译器**。
   于是 run 的 `error` 字段里出现的是 `LLMRateLimited`，而不是让读的人自己去认
   `APITimeoutError`。
5. **顺带发现 `AgentError` 丢掉了异常类型**：`f"LLM call failed in round {n}: {exc}"`
   只用 `str(exc)`，翻译出来的类名被扔了 —— 于是 `stop_reason` 里"稍后再试"和
   "要人去改配置"长得一样。现在消息里带上类名，有测试钉住。

### 三、留给调用方的

`ai_service.generate_cold_email` 现在对每种失败给出**不同的 `fallback_reason`**：
`no_api_key` / `model provider is rate limiting; try again shortly` /
`model call failed and did not recover: ...` / 截断 / 不可用 / 以及
**"unexpected error preparing the email (TypeError): ..."** —— 最后这条是给我们自己的
bug 留的位置，不让它冒充模型问题。有测试断言五种失败给出五种不同的解释。

### 未验证部分

- **没有真的打过限流或断网**：所有分类都是构造异常测的（模块名 + status 都是伪造的
  形状），没有对真实 provider 制造 429/超时。
- **`max_retries=2` 是照 SDK 默认值写的**，不是量出来的：我没有评估过"三次尝试
  是不是太慢"或"退避曲线合不合适"。
- **没有用流式**，所以没验证 SDK 的 SSE 处理 —— 那本来也是选它的理由之一，
  但目前用不上。
- **第四个 provider 没试过**：`base_url` 换 provider 是设计意图，实际只跑过
  OpenAI 兼容的一个端点。
- **`translate_provider_error` 靠鸭子类型**：如果 SDK 未来把异常放到别的顶层模块，
  分类会退化成 `LLMTransient`（仍然在我们的词汇表里，但不够精确）。我没有写
  针对这种情况的告警。

**依据**：`app/llm.py`、`app/agent/protocol.py`、`app/agent/loop.py`、
`app/services/ai_service.py`、`tests/test_llm_seam.py`（新，29 个测试）；
SDK 的异常清单与 `max_retries` 默认值是从装好的 `openai 3.30.0` 上读出来的；
守卫失效是**实测**（去掉 agent 接缝的翻译 → 对应用例变红）；
**680 个测试通过**（原 651），连跑两遍一致。
